1. 交付了什么

DB outbox（WorkflowJob）→ CAS 领取 + 租约→ 统一投递出口→ 阶段状态机→ 运营视图 + 人工接管
本刀要解决的是 T05 之后仍然断掉的**流程可靠性**。四件事：
  • AC-07 幂等：同一业务动作只有一条任务、一条投递 —— 由 (organizationId, dedupeKey) 唯一约束保证；介绍任务是提案级键（不含收件人），通知任务含收件人。
  • AC-09 消息合规：所有对外通知只有一个出口 deliverNotification() —— 它同时负责披露守卫、投递幂等与沙箱判定。站内信真实落库；邮件无凭据时记 CAPTURED，绝不标 SENT。
  • AC-14 端到端：PROPOSED → CONSENT_PENDING → INTRODUCED → COORDINATING → ACTION_COMPLETED → OUTCOME_RECORDED，且只前进不回退。
  • AC-17 崩溃恢复：CAS 领取 + 租约（60s）+ 终态不可复活 + 死信人工接管 + 对账补偿 —— 故障注入下无重复消息。

3. 架构：为什么是「自建 DB outbox」

开工前的阻塞项（已拍板）

BACKLOG §6-⑤ 要求先决定引擎：战略方案给 Temporal，PRD 允许"早期一个可靠的数据库任务队列"。

选 DB outbox，判据是平台约束而非偏好：Temporal 需要常驻进程（worker）， 而 Netlify 免费计划的函数是**临时**的 —— 没有长驻进程可跑。替换点隔离在 runtime.ts 的驱动器接口，日后换引擎不必动业务层。

同一批还拍板了**消息通道**：站内信 + 邮件沙箱（而非仅站内信或真实外发）。

分层（单向无环）

job-core（纯函数·无 IO）
stage-machine（纯函数）   delivery（投递出口）
        ↑                      ↑
  workflow（阶段持久化）──► runtime（引擎）
                               ↑
                           hooks（业务钩子）

纯函数内核让"重试 / 超时 / 死信 / 租约"这些最易错、又最难在集成测试里复现的分支能被秒级穷举。

4. 三个关键取舍（都写在 risks.md 里）

取舍选择为什么
失败分类 三类：retryable / permanent / superseded "提案已被介绍 / 已撤销"不是失败，是"目标已由别的路径达成" → 记 CANCELLED 而非 FAILED。只分两类会让它在监控里长得和"数据损坏"一样。
未知错误默认 retryable（而非 permanent） 投递类失败绝大多数是暂时性的；反向默认会让一次网络抖动永久放弃一条真实通知，且无人发现。代价有 maxAttempts 兜底。
队列里以谁的身份执行 发起提案的运营（不是系统万能身份） 队列只是把"已在运营授权下决定要做的事"延迟执行，不产生新权限。运营已离职/降级 → 停等人接管，而不是由系统越权代做。

5. 故障注入：AC-17 的实际形态

最难的场景不是"任务失败"，而是钩子根本没跑成 —— 提案在那里，却永远不会被通知。E2E 直接构造这个状态：

夹具：cp_e2e_wf_recover —— MUTUALLY_ACCEPTED、introducedAt=NULL、无任何 WorkflowJob
                                    （模拟"钩子失败"）

tick #1  ── 领取并执行既有任务；随后 reconcileMissingJobs() 扫描
            "已双方同意但未介绍"的提案 → 补入队（此时任务已存在，尚未执行）
tick #2  ── 领取并执行那条被补入队的介绍任务 → 介绍落地

断言：introducedAt 非空 · 流程 stage=INTRODUCED · 任务 SUCCEEDED
      · 4 条投递（双方 × 站内信+邮件）· 再跑 tick #3 数量不变（无重复）
为什么要两次 tick：驱动器先执行、后对账。因此"补入队"的任务要到下一轮才执行 —— 这是刻意的顺序（先干完手头的活，再补漏）。用例把这个语义显式写进了注释与断言。

8. 本刀踩到并记录在案的两个坑

① Prisma DateTime 的存储格式

Prisma 经 libSQL 写的是 2026-10-12T06:31:11.687+00:00，而 CURRENT_TIMESTAMP 风格是 2026-10-12 06:31:11（空格分隔）。夹具按后者写 → 引擎的 CAS 等值条件永远命中 0 行 → 任务被安静跳过、停在 PENDING。
教训：凡是会被引擎用作 CAS 等值条件的列，夹具必须写成 Prisma 的格式。

② 路由相对路径的层数

C3 的路由在 workflow/jobs/[jobId]/takeover/（4 段）， _shared 在 workflow/_shared → 应为 ../../../_shared。 照抄 T05 的 3 段写法（../../_shared）会被 tsc 以 TS2307 拦下。
教训：相对 import 路径有 tsc 兜底；路由路径的形状只有 E2E 打真实 URL 能证。
