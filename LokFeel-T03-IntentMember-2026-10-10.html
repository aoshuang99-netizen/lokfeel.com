2. 逐字段披露的四个结构性约束（本任务的核心）

把「不要泄露未授权字段」从一条编码纪律变成一组结构性约束——违反它需要主动绕过三道防线，而不是忘记写一行过滤。
#约束实现违反时会怎样
①缺省 fail-closed 字段未出现在披露表 → 视为 SELF（不对外） 不会"忘了授权就默认公开"，只可能"忘了授权就看不到"
②白名单投影 未授权字段的键在响应对象上根本不存在（不是 undefined） JSON.stringify / 展开 / 深拷贝都不会把它带出去
③SELF 不可能被当成"全量" audienceCanSee(viewer='SELF') 恒 false；ExternalAudience 类型在编译期排除 SELF 误传 SELF 直接 tsc 失败——不依赖运行期测试覆盖
④受保护字段结构性不可授权 email 等标记 disclosable:false + importable:false 写路径 normalizeDisclosure 直接 400，不给"手滑放开"的机会

受众档位是「包含式」的（写反会造成静默的权限反转）

DisclosureAudience:  SELF  <  ORGANIZER  <  COUNTERPARTY
                    仅本人   本人+组织者   本人+组织者+对手方（最宽）

推论：组织者视角 ⊇ 对手方视角
—— 选 COUNTERPARTY 意味着"组织者也能看到"。这条方向写反，就成了
   「更宽的档位反而更保密」，属静默的权限反转，已用矩阵用例锁死。

5. 顺带修掉的真实缺陷（都不是"改一行就好了"的那种）

最值得记的一处：Service Worker 在缓存个人数据，而且"写完立刻读"必然读到旧值。
public/sw.js 对所有 /api/ 的 GET 使用 stale-while-revalidate —— 语义是立即返回缓存副本、后台再更新。于是用户把字段从「组织者」收紧为「仅自己」后， 库里已确认写入 SELF，界面却仍显示「年龄：32」对组织者可见。
为什么难发现：服务端日志里有那次请求且返回 200（SW 确实转发了网络请求）， 单测 / 集成测试 / 类型检查全部正常。只有真实浏览器 + 真实 SW + 连续两次读才暴露。
已修：/api/* 一律不拦截（服务端本就有的 Cache-Control: no-store 这才真正生效）； 默认分支缓存改名 API_CACHE → PAGE_CACHE 消除后门； CACHE_VERSION v3→v4 且 activate 继续清理 api- 前缀 （否则"不再写新缓存"只对新请求生效，设备上旧的那份个人数据副本会永远留着）； 新增 tests/sw-cache-policy.test.ts 7 条源码断言把它钉死。
#缺陷发现方式修复
D1 stableStringify 把 Date 序列化成 {} → 不同 expiresAt 指纹相同 → 幂等误判重放 写 expiresAt 用例时 显式 instanceof Date → toISOString()；补 1 条指纹用例
D2 SW 缓存 /api/ 响应（写完读到旧值 + 个人数据落盘） 移动端 E2E 步骤 ⑧ API 不拦截 + 缓存改名 + 清 api- + 7 条源码守卫
D3 --reset 删库文件与 dev server 句柄冲突 → SQLITE_READONLY（读全对、写全挂） E2E 提交步骤 500 改为同连接 DROP 全表重建，inode 不变
D4 受众档位方向曾实现反了（COUNTERPARTY 只对手方可见） 写包含式语义用例时 统一为包含式；/// 注释固化；矩阵用例锁死
D5 reactivate 缺过期前置检查 → "复活即过期"空操作 状态派生用例 reactivate 且已过期 → 409
