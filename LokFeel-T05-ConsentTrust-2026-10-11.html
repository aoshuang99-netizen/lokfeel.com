1. 交付了什么

ConnectionProposal 模型→ 纯函数状态机内核→ consent / revoke API→ introduce（执行点 · CAS）→ 我的连接（移动端）
把一个「组织者牵线」的产品动作，拆成**可被逐条验证**的三件事：
  • AC-04 单方同意不介绍：第一个同意的人**不能**触发介绍；只有双方都同意（MUTUALLY_ACCEPTED）才可被介绍。
  • AC-05 拒绝与撤销：拒绝 / 撤回立即进入终态；终态之后任何表态一律 409 —— 不是"幂等成功"。
  • AC-06 执行时校验（race condition）：介绍在执行的那一刻重新查提案与双方意图，用**条件更新（CAS）**写入 —— 并发下只有一个能成功。
并顺手接通了 T04 留下的一个悬空档位：COUNTERPARTY（用户授权给"已同意的对手方"的字段），在本刀之前**没有任何读路径**。

2. 三条 AC 各自被什么证明

每层能证伪的失败形状不同 —— 任何一层都替代不了另一层。
AC一句话主判据独立佐证
AC-04 单方同意不产生介绍 纯内核 resolveStatusAfterDecision()（4 例）+ 服务层负测（11 例） E2E：点同意 → 状态仍「待决」；双方同意 → 「等待介绍」仍非已连接
AC-05 拒绝即关闭；撤销阻止后续 服务层 + HTTP 层状态码（14 例） E2E：拒绝 → 已拒绝；撤回 → 已撤回；两者动作区消失
AC-06 执行时再校验（race） 纯函数 evaluateIntroducibility() + updateMany CAS 写入 E2E：运营介绍 → 200 建立连接；重复介绍 → 409
为什么把 AC-04 抽成纯函数。AC-04 的全部内容就是一条状态转移规则。写成服务层里的 if，就只能靠起数据库来验证； 抽成 resolveStatusAfterDecision(谁, 决定, 双方表态) 之后，这条规则有了 12 个 0.3 秒跑完的断言， 而且任何调用方都绕不过它 —— 这正是"最容易写错的那一处"应有的形状。

5. 关键设计决策

决策为什么
CONSENT_PENDING 跨越第一次 accept 最常见的错误是把 accept 写成"状态 = ACCEPTED"，于是谁先点谁触发。判据始终是「双方均已同意」。
终态后表态 → 409（不是幂等成功） 若"'拒绝'之后再'接受'"被静默接受，用户会以为自己改变了主意，而对方早已收到拒绝 —— 这种"两端认知不一致"比显式报错危险得多。
执行时校验 = 重新查 + CAS 写 "先查再写"在并发下仍会双写。updateMany({ introducedAt: null, status: 'MUTUALLY_ACCEPTED' }) 把"再校验"与"写入"合并成一条原子语句，并发只有一个能成功。
披露档位随阶段升级 升级判据是 introducedAt !== null，不是"双方点了同意"。若写成"同意即升级"，用户只授权给「已同意对手方」的字段（如年龄）会在还没被介绍时就泄露。降级即刻生效，不需要定时任务。
introduce 刻意不带幂等键 介绍是一次性事实，"再介绍一次"本身就是错误请求 —— 正确的答复是 409，而不是"回放上次结果"。给它幂等键反而会把"第二次点击"伪装成成功。
拒绝理由不回流 ProposalDecision.note 只落库供审计，不返回给对侧 —— 否则"拒绝理由"就成了一次计划外的信息披露。

7. 把 E2E 从「偶发红」修成「稳定绿」的三处竞态

7.1 登录不加载登录页

用 browserContext.request.post('/api/auth/login') —— 它共享上下文的 cookie 罐， 后续 ctx.newPage() 天然是已登录态，全程不加载任何 HTML 页面。 打的仍是同一个端点、带同一个 Origin，没有绕过被测逻辑。

7.2 以 POST 响应为锚点，不以瞬态提示为锚点

首个写请求在 dev 下可能现场编译到 68 秒（指纹：POST …/consent 200 in 68s (next.js: 67s)）—— 慢的是框架编译，不是业务代码。"等 POST 响应"天然不受编译耗时影响。

7.3 「用户能看到的」≠「刷新后仍成立的」

这条值得单独记。断言"用户能看到的"（瞬态提示、过渡态）的用例，在 dev 下必然偶发； 只有"刷新后仍然成立"的持久事实（分区归属、终态、有无动作区）才是可以长期守住的判据。

8. T04 回归：登录页脆弱性与等价复验

candidate-match.spec.ts 的第 2/3 例用 loginViaUi() 走真实登录页。 在本机 dev 下连续 2 轮失败，失败点在登录、不在候选页：登录页的受控组件在 hydration 完成前接受 fill() 却不让 React state 更新，提交时前端校验报"字段为空"，3 次重试都拿不到 session-token。
结论：这是登录页的脆弱性，与候选页断言无关（它根本没执行到候选页）。 为把"登录方式"这个无关变量消除掉，新增可复跑脚本 scripts/qa/verify-t04-candidate-regress.mjs，用同一套 ctx.request 手法复验 —— 15 / 15 通过，其中包含 T05 真正改动的 ④ 三条断言 （matches-connect-note / matches-view-proposals 可见、propose-open 不存在）。

建议：T12 端到端门禁把 E2E 登录统一切到 ctx.request 手法，消除这一类与业务无关的抖动。
