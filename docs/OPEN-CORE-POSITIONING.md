# 开源定位与内容中立政策 (Open-Core Positioning)

> 状态：**待评审定稿** · 2026-09-27
> 这份文档回答一个决定项目生死的问题：**我们开源的是什么，不开源的是什么，以及为什么。**

---

## 1. 一句话定位

> **一个可自托管的关系匹配与社群平台引擎 —— 开源核心、内容中立、部署方自治。**

### 1.1 三个关键词的含义

| 关键词 | 含义 | 反面（我们不做什么） |
|---|---|---|
| **可自托管** | 一条 `docker compose up` 就能跑起来，不依赖任何我们的服务 | 不是"必须用我们的云才能跑" |
| **内容中立** | 仓库只提供能力，不含任何用户内容、成人素材或运营数据 | 不是"一个成品成人交友站" |
| **部署方自治** | 数据、收款通道、合规责任都在部署方手里 | 不是"数据默认回到我们这里" |

---

## 2. 为什么必须内容中立（这不是价值判断，是生存问题）

### 2.1 平台政策风险

主流平台的可接受使用政策（AUP）普遍禁止 obscene / sexually exploitative 内容：

| 平台 | 政策要点 | 对我们的影响 |
|---|---|---|
| GitHub | AUP 禁止 sexually obscene content | 仓库本身若含成人内容素材，**仓库会被下架** |
| AWS | AUP 禁止 obscene / otherwise objectionable 内容 | 部署在 AWS 的官方演示环境会被停用 |
| Vercel | AUP 禁止 obscene 内容，非企业版不得用于 objectionable purpose | **已发生过同类事故**（本项目曾因账户问题导致部署被暂停）|

**结论**：仓库必须保持"能力开放、内容中立"。禁的是**内容**，不是**话题** —— 我们完全可以讨论关系结构、匹配算法、隐私保护，但不能把成人素材放进仓库。

### 2.2 支付通道风险

已确认的高风险点（详见 `docs/PAYMENT-COMPLIANCE.md`）：

- 主流国际通道（Stripe 等）将成人内容列为**禁止类**
- 现有主力通道的条款据检索**禁止交友网站服务**
- 能承接成人品类的高风险通道**不足 50 家**，拒付率约 2.1%–3.4%

**结论**：开源版**不应内置任何默认支付通道**。正确做法是 **BYO Gateway**（部署方自带已获批的通道），让资金与合规责任留在部署方。

### 2.3 声誉与人才风险

一个被标记为"成人交友站"的仓库：

- 会劝退绝大多数潜在贡献者（企业开发者尤其敏感）
- 会缩小可触达的客户范围（政企、医疗、金融类客户直接排除，而这正是客单价最高的一层）
- 会让每一次商业合作都要额外解释成本

## 3. 开源边界（开源什么，不开源什么）

### 3.1 ✅ 开源核心（AGPLv3）

这些是"一个社群平台要有的一切"，也是我们认为的公共品：

| 模块 | 说明 |
|---|---|
| 匹配引擎 | 关系结构匹配算法、评分、配额（`src/lib/matching/*`）|
| 用户与档案 | 注册、登录、档案、Onboarding |
| 实时通信 | IM（已读/在线/输入中/回应）、WebRTC 音视频通话 |
| 社群基础 | 会话、通知、举报、拉黑、事件 |
| 管理后台 | RBAC（61 权限码 / 7 角色）、审核、审计日志 |
| 支付框架 | `PaymentProvider` 抽象层（**不含任何通道凭证**）|
| 多租户 | 租户模型、隔离机制、白标配置 |
| 部署交付物 | Dockerfile、Compose、Helm、迁移脚本、文档 |

### 3.2 💰 商业版（企业许可）

付费点必须落在"规模化 / 合规 / 企业级"，而不是把基础功能打残：

| 模块 | 为什么收费 |
|---|---|
| SSO / SAML / LDAP / SCIM | 企业采购的硬门槛；且与开源版的其他能力无冲突 |
| 完整审计与合规导出 | GDPR 数据主体请求、审计归档；面向有法务要求的客户 |
| 多租户隔离的高级形态 | 更强隔离、跨租户运营工具 |
| 反诈骗 / 风控引擎 | 真正的护城河（不是算法，是信任与安全）|
| 年龄验证模块 | 对接第三方验证服务（成本与集成复杂度高）|
| 高可用 / 集群 / air-gapped | 只在大型部署中需要 |
| SLA 支持 | Linux Foundation 调研：54% 视付费支持为刚需 |

### 3.3 🔌 可选插件（**不进入主仓库**）

以下能力做成插件，由部署方自行启用并承担责任：

| 模块 | 为什么必须下沉 |
|---|---|
| **成人内容合规模块** | 18 USC 2257 记录保存、DMCA 流程、创作者协议 —— 这些是**运营方**的义务，不是引擎的义务 |
| **机器人 / 演示账号体系** | 与开源信誉直接冲突（详见 §4）|
| 特定支付通道的深度集成 | 通道条款各异，且部分通道禁止特定业务 |
| 地域封禁策略 | 硬编码地域规则会误伤正常部署 |

## 4. 关于机器人体系（Bot System）的特别说明

当前代码库包含完整的 Bot 体系（`BotProfile`、`BotInteractionLog`、`BotLearningBatch` 等 6 张表 + `api/bot/*` + `api/cron/bot-*` 路由），运营数据记录 Bot 约 3,500 个 + 遗留 Bot 约 7,332 个。

**开源前的处置决策：**

| 处置 | 说明 |
|---|---|
| 从核心 schema 移出 | 6 张表移出核心 schema，可减少约 14% 的多租户改造量 |
| 改为默认关闭的可选模块 | 默认不编译、不启用 |
| 不携带任何 Bot 生成数据 | 仓库与镜像中不得含任何 Bot 数据 |
| 文档明确用途 | 定位为"演示与压力测试工具"，并明确生产环境启用的信任风险 |

**为什么不保留在核心：**

1. 一个"用户数靠机器人堆出来"的系统，会立刻成为舆论攻击点
2. GitHub AUP 对欺骗性设计敏感
3. 我们对外公布的用户数据必须干净 —— 新官网**不应引用任何含 Bot 的用户数字**

### 4.1 实施进度（2026-09-28 更新）

四项处置里，**第 1、2 项已落地并验证**。

| 处置 | 状态 | 证据 / 说明 |
|---|---|---|
| ① 从核心 schema 移出（6 张表） | ✅ **已完成** | schema 拆分为多文件目录 `prisma/schema/`（`core.prisma` 42 张核心表 + `bot.prisma` 6 张 Bot 表 + 4 个 Bot 枚举），同一 Prisma client、业务代码零改动。**注意**：`BotProfile.profileId` 降级为普通列（DB 侧 FK 保留），核心 `Profile` 不再声明反向关系 —— 这是拆分的必要代价，按 userId 反查 BotProfile 改两步查询（`bot-gate.ts` / `bot-automation.ts` 已重写）。DB 侧建表走 `prisma migrate diff` + 差集同步（`db push` 对远程 libSQL 不可用） |
| ② 改为默认关闭的可选模块 | ✅ **已完成** | `src/config/bot-policy.ts` 单一配置源 + `npm run verify:bot` **109 项通过**。改造前**没有任何总开关** —— 想关掉只能去各部署平台逐条删定时任务，删漏一条 Bot 就继续写库 |
| ③ 不携带任何 Bot 生成数据 | ✅ **已完成（2026-09-28）** | `public/bot-avatars/`（1219 张 / 9.3MB）已移出仓库（`.gitignore` + `git rm --cached`，本地保留供维护脚本）；DB 复核 0 个用户指向该目录；`.dockerignore` 显式排除 `backups/` 与 `public/bot-avatars/`；`prisma/seed.ts` 清理列表移除已删除的 Legacy 三表。`scripts/import-bot-*.mjs` 不存在（历史记录有误） |
| ④ 文档明确用途与信任风险 | ✅ 已完成 | `docs/SELF-HOSTING.md` §5.6；本节即风险说明 |

**关于默认值的最终状态（2026-09-28 翻转，必须写清楚，否则下一个人会改错）**：

| 层面 | 默认 | 说明 |
|---|---|---|
| **代码**（`BOT_ENGINE_ENABLED` 未设置） | **关闭** | 2026-09-28 独立提交翻转。翻转时受影响部署必须显式设 `BOT_ENGINE_ENABLED=true`；本 C 端生产（Netlify `lokfeel` 站点）已在翻转前于站点级 env 设好 `true`（production / branch-deploy / deploy-preview），故线上 Bot 不中断 |
| **发行物**（`.env.example` / `docker-compose.yml`） | **关闭** | 未变。自托管者 `cp .env.example .env` 得到的就是关闭状态 |

两者由 `npm run verify:bot` 的反回归守卫钉死（含「未设分支返回 false / source=default」的源码锚点断言，
防止将来无意改回启用）。**注意**：Netlify 免费计划不能通过 API 设账号级共享变量（403），
但站点级 env 可用 —— `POST /accounts/{slug}/env?site_id={id}`，body 为数组且**省略 scopes**。

另一个刻意的行为：**取值无法识别时按 `false` 处理（fail-closed）**。
`BOT_ENGINE_ENABLED=flase` 不会"当成启用"，而是关掉模块并把原始取值写进
`/api/health` 的告警。理由同上 —— 一个拼错字母就关不掉的开关不算开关。

## 5. 许可策略

| 组件 | 许可 | 理由 |
|---|---|---|
| 社区版 | **AGPLv3** | 唯一能约束"云厂商直接托管变现"的 OSI 开源许可，同时不损失开源信誉 |
| 企业版 | 商业许可 | 见 `LICENSE-COMMERCIAL` |
| 文档 | CC BY 4.0 | 便于传播与翻译 |
| 商标 | 保留 | 见 `TRADEMARK.md` |

**为什么不用 BSL / SSPL：** HashiCorp、Elastic、MongoDB、Redis、MinIO 五个"收紧许可"案例中，**没有一个证明带来了收入拐点**，反而全部触发社区 fork；Elastic 与 Redis 均在两年内回退 AGPLv3。详见可行性研报的市场分析章节。

## 7. 与现有 C 端业务的关系

这是必须想清楚的一件事：

| 问题 | 建议答案 |
|---|---|
| 开源版会蚕食现有 C 端订阅收入吗？ | 影响极小 —— 现有 C 端收入规模有限，而开源版面向的是完全不同的买家（运营者而非终端用户）|
| 现有 C 端产品继续运营吗？ | 建议继续，作为现金流基本盘与技术验证场，但**不用它的用户数据做开源宣传** |
| 现有 Bot 数据怎么处理？ | 不进入开源仓库；官网与开源宣传材料不引用 |
| 两个产品的品牌关系？ | 明确区分：开源版是**引擎**，C 端是**用这个引擎运营的一个实例**（由我们自己运营）|
