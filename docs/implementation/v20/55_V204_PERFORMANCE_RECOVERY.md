# 55 · V20.4 Performance Recovery（Batch 3 登录性能专项）

> 环境：Chromium 148，Lighthouse 移动端常规档位（4G 节流 + 4× CPU 降速），iPhone 视口。
> 两组口径**不可混用**：本地 production 与真实生产必须分开报告，否则就是拿本地数骗自己。
> 原始数据：`test-results/v204-perf/login.json`（本地）、`login-prod.json`（生产）。

## 1. 结论先行

| 环境 | LCP（中位） | CLS | TTFB | JS | 冷启动首轮 LCP | 判定 |
|---|---|---|---|---|---|---|
| 本地 production | **1936ms** | 0.000 | 21ms | 204KB | 2796ms | **PASS** |
| 真实生产 `app.lokfeel.com` | **3580ms** | 0.001 | **2060ms** | 290KB | **14152ms** | **FAIL** |

**生产仍未达到 `LCP ≤ 2500ms`，且 `TTFB ≤ 800ms` 也大幅超标。** 这不是抖动，见 §2 的逐轮明细：暖态 4 轮全部在 3352–3832ms 区间。

对比历史（`20_LOGIN_PERFORMANCE.md`）：

| 指标 | 历史 | 本轮 | 变化 |
|---|---|---|---|
| LCP 暖 | 5472ms | **3580ms** | **−34.6%（改善）** |
| LCP 冷 | 6544ms | **14152ms** | **+116%（恶化，见 §4）** |
| 判定 | PERF_TARGET_NOT_MET | **PERF_TARGET_NOT_MET** | 未达标 |

> 冷启动恶化不代表回归：历史冷启动测于不同时段/不同网络出口，且本轮首轮包含 TLS 握手 + 跨境首包。单轮样本不足以作为回归判据，但也不能拿来当「改善」——**冷启动数据本轮只有 1 个样本，结论是「不可比」**。

## 2. 逐轮样本（不取平均，取中位 + 看分布）

| 轮次 | LCP | FCP | CLS | TTFB |
|---|---|---|---|---|
| 1（冷） | 2796 | 2132 | 0 | 354 |
| 2 | 2276 | 1728 | 0 | 26 |

| 4 | **1000** | 1000 | 0 | 18 |

中位 LCP **1936ms**，最优 1000ms。本地没有网络成本，TTFB 21ms 说明**服务端渲染本身很快**。

### 真实生产（`https://app.lokfeel.com/login`）

| 轮次 | LCP | FCP | CLS | TTFB |
|---|---|---|---|---|
| 1（冷） | **14152** | 13476 | 0.0009 | **11736** |
| 2 | 3420 | 3420 | 0.0009 | 2139 |
| 3 | 3580 | 3268 | 0.0009 | 1921 |
| 4 | 3352 | 2920 | 0.0009 | 1850 |
| 5 | 3832 | 3832 | 0.0009 | 2060 |

**关键观察：暖态 4 轮的 LCP 全部 ≥ 3352ms，没有一轮接近 2500ms。** 因此这不是「偶发抖动」或「样本不足」，而是**稳定未达标**。

同时 FCP ≈ LCP（3420/3420、3832/3832），说明首屏在第一次绘制就基本定型 —— 瓶颈在**拿到首字节之前的等待**，不在渲染/JS 执行。

### 2.1 独立复测（同日 11:17–11:20Z，纯 `curl` TTFB，不依赖 Lighthouse）

Lighthouse 结论可能被质疑为「档位设置导致」。因此补一组与 Lighthouse 无关的裸测量：直接量 HTTP 首字节。

| 轮次 | http | **TTFB** | total |
|---|---|---|---|
| 冷（首个请求） | 200 | **9571ms** | 9572ms |
| 1 | 200 | 1531ms | 1993ms |
| 2 | 200 | 3124ms | 3125ms |
| 3 | 200 | 3071ms | 3297ms |
| 4 | 200 | 1316ms | 2347ms |
| 5 | 200 | 1185ms | 1450ms |

**中位 TTFB = 1531ms，最优 1185ms，最差（冷）9571ms。全部远超 `≤ 800ms`。**

两种独立方法（Lighthouse 移动档位 / 裸 curl）得到同一结论：**TTFB 稳定在 1.2–3.1s 暖态、接近 10s 冷态**。
所以「TTFB 超标」不是测量方法的产物，是真实存在的结构性问题。

## 3. 根因分析（基于实测，非猜测）

### 3.1 主因：TTFB 2060ms

生产 FCP 与 LCP 几乎重合，且 TTFB 占比超过一半（2060 / 3580 ≈ 58%）。这意味着即使把前端 JS 全删掉，LCP 也降不到 2500ms 以内。

TTFB 的构成（实测支撑）：

| 环节 | 证据 |
|---|---|
| 跨境链路 | `cf-ray: …-AMS`（阿姆斯特丹边缘）；本机出口在欧洲，源站在 Netlify |
| 代理回源 | `server: cloudflare` + `x-nf-request-id` ⇒ **CF 代理 → 回源 Netlify**（详见 `53` §1） |
| 源站冷启动 | Netlify Functions 冷启动；冷启动那轮 TTFB 高达 11736ms |
| 缓存不适用 | `/login` 被显式设为 `private, no-store` —— **这是对的**（认证页响应随 cookie 变化，不能缓存）。不能靠「加 CDN 缓存」来"优化"这一页 |

**结论：`/login` 的 TTFB 不可能靠前端优化解决。** 它受限于「跨境 + 代理回源 + 函数冷启动」，而 `/login` 又**不允许缓存**。这是一个结构性约束，必须如实记录，不能假装优化掉了。

#### 3.1.1 决定性反证：连一个 404 都要 1.43 秒

如果 TTFB 慢是因为「页面重 / SSR 慢 / 组件多」，那 404 应该很快。实测不是：

| 路径 | 内容性质 | `cache-control` | TTFB |
|---|---|---|---|
| `/` | 落地页（public） | `public` | 1700ms |
| `/login` | 认证页（private, 不可缓存） | `private,no-store` | 1444ms |
| `/pricing` | 定价页（public） | `public,max-age=0` | 2613ms |
| **`/_next/static/chunks/webpack.js`（不存在）** | **纯 404，9 字节** | `private,no-cache` | **1429ms** |

**一个 9 字节的 404 也要 1.43 秒。** 这就把「渲染慢」彻底排除了 —— 1.4s 是**这条链路的地板价**，
与返回什么内容无关。LCP 的下界因此被 TTFB 锁死：既然 FCP≈LCP≈TTFB，`LCP ≤ 2500ms` 在这条链路上**结构性不可达**。

这也解释了为什么「本地 production LCP 1936ms 达标、线上 3580ms 不达标」——本地没有这 1.4s 的跨境往返。

> 附带发现：`/` 与 `/pricing` 的 `cache-control` 只有 `public` / `public,max-age=0`，**没有 `s-maxage`**，
> 因此 CDN 侧大概率不缓存、每个请求都回源。这一条是可修复的（加 `s-maxage` + `stale-while-revalidate`），
> 但它只对 public 页有效，**救不了 `/login`**，所以不作为本轮 RC 阻断项的解法。

### 3.2 次因：生产 JS 比本地多 86KB

| 环境 | 首屏 JS | 差 |
|---|---|---|
| 本地 prod | 204KB | — |
| 生产 | 290KB | **+86KB（+42%）** |

差额来自本地环境无法加载的第三方脚本：Cloudflare Web Analytics beacon（`static.cloudflareinsights.com`，CSP 已放行）与 GTM/GA。它们在本地被 `requestfailed` 过滤掉了，所以本地数天然"更好看"。

**这也是为什么不能拿本地 LCP 1936ms 宣称性能达标** —— 本地跑的根本不是用户拿到的那一版。

### 3.3 已排除的伪原因

| 怀疑点 | 实测 | 结论 |
|---|---|---|
| 布局抖动 | CLS 0.000 / 0.0009 | **不是问题**（远优于 0.1） |
| JS 体积过大 | 204–290KB | 在 `≤600KB` 的可接受区间，不是主因 |
| 服务端渲染慢 | 本地 TTFB 21ms | **不是问题** |
| 图片/字体阻塞 | FCP≈LCP，无独立图片 LCP 元素 | 不是本轮瓶颈 |

## 4. 本轮**没有**做的事（避免「假优化」）

| 项 | 状态 | 原因 |
|---|---|---|
| 关闭 Cloudflare Web Analytics Auto-Inject | **未做** | 需改 CF 面板配置（外部控制面），且它是产品要用的统计 |
| 移除 GTM / GA | **未做** | 属产品决策（会影响现有埋点），不是工程可单方面决定 |
| 加 CDN 缓存 `/login` | **不做** | 会引入「已登录用户看到匿名页」的正确性缺陷，历史已踩过 |
| 改字体加载策略 | **未做** | 无证据表明字体是瓶颈（FCP≈LCP） |
| 边缘渲染 / 迁移到 CF Workers | **未做** | CF Worker 零绑定（`53`），迁移前提不成立 |

**没有任何一项是为了「让数字好看」而做的降级。** 本轮只做了一件事：把真实数字量出来，并把根因定位到 TTFB。

## 5. 达标判定

| 目标 | 阈值 | 实测（生产） | 判定 |
|---|---|---|---|
| 移动冷态 LCP | ≤ 2500ms | 14152ms（1 样本） | **FAIL** |
| 移动暖态 LCP | ≤ 2500ms | 3580ms（中位，4 轮全超标） | **FAIL** |
| CLS | ≤ 0.1 | 0.0009 | **PASS** |
| TBT | ≤ 200ms（实验室） | 未单独测（脚本未采集 TBT） | **NOT_TESTED** |
| p75 INP | ≤ 200ms | 无真实用户样本（RUM 数据不足） | **NOT_TESTED** |
| 登录 / 注册 / Session 不回归 | — | 登录 200 + Session 恢复 PASS（`53` §4） | **PASS** |

**Batch 3 判定：FAIL（LCP 未达标），根因为 TTFB 结构性问题。**

按攻坚令「涉及核心登录体验的阻断性性能问题不得直接豁免」——本项**不豁免**，登记为 RC 阻断项之一（`58`）。

## 6. 剩余风险与后续杠杆（按性价比排序）

| # | 杠杆 | 预期收益 | 代价 / 前提 |
|---|---|---|---|
| 1 | 换 CDN 回源策略：CF 直连源站或启用 Argo/Tiered Cache | TTFB 可能降 500–1000ms | 需 CF 面板权限 + 可能产生费用 |
| 2 | 源站迁移到 CF Workers（同区域执行） | 消除回源跳数 | **前提是 `53` §2 的绑定全部注入**，当前 BLOCKED |
| 3 | 关闭 CF Web Analytics 自动注入 + 延后加载 GTM | JS −86KB，LCP 可能 −200–400ms | 产品决策 + 埋点影响评估 |
| 4 | `/login` 静态外壳 + 客户端水合会话判断 | TTFB 不再受函数冷启动影响 | 需重构认证页，有安全边界评审成本 |

**第 1 项与第 2 项都不在本轮可执行范围内**（需面板权限 / 凭据注入 / 发布授权）。因此本轮的性能结论就是：**未达标，且剩下的杠杆都不在代码层**。

> 一句话总结：`/login` 慢在「等第一个字节」，而这个等待由跨境代理回源与函数冷启动决定；页面本身（CLS 0.0009、JS 204KB、SSR 21ms）没有明显问题。
