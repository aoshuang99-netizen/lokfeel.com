# T08 · risks — 风险与残余

> 基线 `95da9f1`（`main`，已发布生产）。本文只记**会长期存在的残余**，
> 不记"已修好的 bug"（那些进 `changes.md`）。

---

## R1 · AC-21 真实支付能力缺失 🔴 高（**外部依赖，不可自解**）

**风险**：Creem 凭据（`CREEM_API_KEY` / Webhook secret / 两个 `PRODUCT_ID`）未提供
（用户已决定暂不提供）。因此：

- 沙箱能证明的：**"要发给 Creem 的请求长什么样"**（落库为 `CAPTURED` 快照）、
  状态机在 `PENDING → SUCCEEDED / FAILED / REFUNDED` 之间的**非法迁移会被拒**、
  用量可复算；
- 沙箱**不能**证明的：真实扣款、真实退款、真实 webhook 幂等、真实升降级生效。

**影响**：`AC-21` 只能标 **`BLOCKED`**，**不得标 PASS**（BACKLOG §6-⑦ 已拍板）。

**缓解**：适配器与业务状态机分离 —— 接上凭据时**无需改业务代码**，
只需把"捕获"换成"真实调用"（与 T06 邮件沙箱同一手法）。
本文与 `plan.md` §7 都显式写明这一点，避免日后有人把沙箱绿当成 AC-21 通过。

## R2 · 验证级别是"派生快照"，存在写回延迟窗口 🟡 中

**风险**：`Outcome.verificationLevel` 是**落库的派生快照**（由 `deriveVerificationLevel`
从 `OutcomeVerification` 记录集算出后写回）。写记录与写快照是**两条语句**，
中间若进程被杀，快照会滞后于记录集。

**影响**：极端情况下"已验证"过滤（下推 SQL 到快照列）会漏掉一条**其实已被确认**的成果，
直到下次有人对它做确认/核验触发重算。

**缓解**：
- 快照只用于**过滤与列表展示**；`deriveVerificationLevel` 始终是**权威**（记录集永远正确）；
- 写回用 `updateMany`（不抛错也不重试），因为**记录集才是事实**；
- 若未来要收紧：把写回放进与 `create` 同一事务（当前 libSQL 无跨语句事务保证，
  属 §5 的 M6 目标范围）。

**残余**：接受。列为已知不精确点，不假装"快照永远等于记录集"。

## R3 · 阶段机接线是"尽力而为"，可能上报成功但阶段未推进 🟡 中

**风险**：`reportOutcome` / `confirmOutcome` / `verifyOutcome` 里的
`advanceIntroductionWorkflow(...).catch(() => {})` —— 与 T06 的钩子同一取向：
**入队/推进失败不把已成功的业务操作变成 500**。

**影响**：成果已落库，但连接的阶段停在原地（例如仍是 `INTRODUCED`）。
运营视图会把它显示为停滞，由人处置 —— **不会静默数据损坏**。

**为什么这样选**：反过来（推进失败就整体回滚）会让"成果上报"在队列抖动时失败，
用户以为没上报成功于是再点一次 —— 而那次会撞 409（一个提案一份成果），
体验更坏，且同样没解决问题。

**残余**：需要一条"阶段滞后"的对账（与 T06 的 `reconcileMissingJobs` 同类）。
当前靠运营视图的停滞标记兜住。

## R4 · 新建计费域，与既有 B2C `Subscription` 并存 🟡 中

**风险**：仓库里现有一套**个人 B2C** 的 `Subscription` / `Payment`（Stripe 字段、
`userId` 归属）。T08 新增的是**组织级**计费域。两套并存，靠命名与注释区分。

**影响**：新人（或未来的我）可能误把 `Subscription` 当作"社群订阅"来实现 T08 后续需求，
从而污染既有查询（"这个用户是不是会员"会悄悄包含社群订阅）。

**缓解**：
- `prisma/schema/outcome.prisma` 文件头**显式写明"为什么不复用"**（三条理由）；
- 两套的字段命名刻意不同（`userId` vs `organizationId`），且 T08 侧不引入任何 Stripe 字段；
- 收敛计划留到 M6 之后（与 REUSE_MATRIX 的其他收敛项一起）。

## R5 · `Outcome.summary` 对全员可见，内容可能含 PII 🟡 中

**风险**：`outcome.read` 是 **SELF_SERVICE**（MEMBER 起即有），而 `summary` 是
上报方自由填写的内容。理论上有人可以在里面写下对方姓名/联系方式。

**影响**：一次计划外的信息披露（与 T05「拒绝理由不回流」要防的是同一类问题）。

**缓解**：
- **userId 一律不进 DTO**（只给角色）—— 关系数据本身不泄漏；
- 审计**不落 summary 原文**，只落标识；
- `evidence` 与 `note` **一律不外发**（只在服务端与审计面）；
- summary 长度上限 1000 字，抑制"粘贴整份档案"。

**残余**：summary 的自由文本无法在服务端做语义脱敏。接受，并在 Console 屏文案里
提示"这是社群可见的成果陈述"。若日后要更严，可把 summary 收窄到"仅当事方 + OPERATOR+"。

## R6 · 一个提案只落一份成果（`@@unique([proposalId])`）🟡 中

**风险**：`Outcome.proposalId` 唯一 → 一条连接只能有一条成果记录。真实的连接可能
产生多个阶段性成果。

**影响**：第二次上报被拒（409）。用户被告知"已有成果"，但没有"追加"的路径。

**取舍理由**：`OUTCOME_RECORDED` 是阶段机的**终态**（不可逆），一份连接一份成果
与"终态"语义一致；允许多份则需要把阶段机改成可回退，或引入"成果修订"概念 ——
那是更大的改动，且与 AC-15 的"三级验证"正交。

**残余**：接受。若产品上确认需要多条，扩成 1:N 时 `OutcomeVerification` 的结构无需变。

---

## R7 · `occurredAt` 允许回填，存在"改口径"空间 🟡 中

**风险**：成果发生时间由上报方填写（允许晚于此刻补报），因此按日期分桶的商业指标
可以被上报方通过填不同日期"搬运"。

**影响**：AC-16 的漏斗/成本按 `occurredAt` 分时段时，数字可被有意无意地移动。

**缓解**：
- 硬约束：`occurredAt` **不得早于**介绍时间（服务层判定 → 400）；
- `createdAt`（系统看见的时间）与 `occurredAt`（业务时间）**分开存**，
  指标口径必须在文档里明确取哪一个；
- 审计记录两者。

**残余**：接受。指标口径已写明，不做服务端猜测。

---

## R8 · 成果列表 `limit ≤ 200` 且无分页 🟡 低

**风险**：`GET /api/v1/outcomes` 是"取最近 N 条"（默认 50，上限 200），响应里
**没有** `total` / `truncated`（与 T07 的 pipeline 不同 —— 那里有）。

**影响**：成果超过 200 条时，用户看不到更早的记录，且**界面不会说明被截断**。

**缓解**：Console 屏文案写明"本屏只列最近 N 条"。

**残余**：Slice 2 做"商业指标"时会引入聚合端点，届时一并补分页与 `truncated`
（与 T07 的诚实口径对齐）。**已记入待办**。

## R9 · `outcome.verify` 是运营动作，可能被用来"洗白"自报 🟡 中

**风险**：ADMIN+ 可以对**任意**成果做外部核验（不需要是当事方）。一个管理员的误判
会把一条自报直接抬到 `EXTERNALLY_VERIFIED`。

**影响**：AC-15 的"三级分离"在**信任管理员**这一层上没有技术防线。

**缓解**：
- 核验**必须留痕**：`OutcomeVerification` 是不可变记录，含 `actorId` + 时间；
- 审计 `outcome.externally_verified`（含 `hasEvidence`）；
- 界面显示**完整的验证轨迹**（谁在哪天把级别抬到哪一档）—— 误判可被追溯与追责。

**残余**：接受。技术只能保证"可追溯"，不能保证"判断正确"。

---

## R10 · 指标口径的两个刻意取舍：**无时间窗口** + **快照式漏斗** 🟡 中（Slice 2）

**风险**：`GET /api/v1/outcomes/metrics` 目前

1. **不做时间窗口**（`basis.scope = 'all-time'`）—— 没有"本月/本周"这类时段筛选；
2. 漏斗是**当前状态快照**：`mutuallyAccepted` 数的是"此刻 `status = MUTUALLY_ACCEPTED`"，
   **包含已介绍的**；`REVOKED` 的提案**不计入任何一档**（哪怕它曾经双方同意过）。

**为什么不做时间窗口**（这不是偷懒，是避坑）：库里的 DateTime 是 **TEXT 且格式不统一**
（Prisma 写 `...+00:00`、早期脚本写 `...Z`、`CURRENT_TIMESTAMP` 风格是空格分隔）。
跨格式的**范围比较**会给出**静默错误**的计数 —— 而静默错误的计数正好摧毁 AC-16。
时段口径要与 `UsageRecord`（时间列由我们自己写）一起做，届时才可控。

**影响**：想看"本月新增了多少连接"暂时做不到；漏斗也不能回答"历史队列里有多少条曾双方同意"。

**缓解**：
- 口径**写进响应**（`basis.scope`）与 `metrics.ts` 文件头，不让调用方靠猜；
- `?missionId=` 提供了唯一一种收窄，且它是**格式无关**的等值过滤（安全）；
- 快照式漏斗的每一档都能用**一条 SQL** 复算 —— 这正是 AC-16 的可复算前提。

**残余**：接受。Slice 3 引入 `UsageRecord` 时补时段口径。

## R11 · 成本指标对**全成员**可见 🟡 中（Slice 2）

**风险**：`outcome.read` 是 SELF_SERVICE（MEMBER 起即有），而 `metrics` 端点 gate 的正是它
（`plan.md` §6 的口径：指标与成果列表同权限）。因此 **MEMBER 能看到本社群的推论成本**
（`cost.totalCost` / 各单价）。

**影响**：单价与总成本属于**经营信息**，理论上不该让所有成员看到。

**缓解**：随 `plan.md` §6 的既定口径执行（一致优先）；`unitCostsCents` 是**假设**
（见 R12），不是真实采购价，泄漏的实际信息量有限。

**残余**：**待产品拍板** —— 若要收紧，可把 `cost` 单独 gate 到 `workflow.read`（OPERATOR+）
或新增 `outcome.cost.read`，而不动 `funnel` / `workload`。这是一行守卫的改动，
但会让"指标"变成两个端点，故先按 §6 执行并在此留痕。

## R12 · 单价与工时是**假设**，不是财务事实 🔴 高（Slice 2）

**风险**：`METRIC_ASSUMPTIONS` 里的 `unitCostsCents`（20/500/300/100 分）与
`minutesPerIntervention`（15 分钟）**都是占位假设**，没有任何外部系统为依据。

**影响**：`cost.totalCost` / `estimatedHumanHours` 是**量级参考**，
**不能**用于对外报价、结算或财报。

**缓解（本切片的核心设计）**：
- 假设**随响应下发**（`basis.assumptions`）—— 看到数字的人同时看到它的依据；
- 假设**可注入**（`computeOutcomeMetrics(counts, { assumptions })`），
  且测试里有**变异自证**：换掉假设必须让工时/成本跟着变（否则"可配置"是假的）；
- 对账脚本**从响应读假设**去复算，而不是自带一份常量 —— 否则"改代码没改脚本"会让
  两边同时错、互相盖章。

**残余**：Slice 3 接真实计量后，应把假设改为**按租户配置读取**（`UsageRecord` + 费率表）。
在此之前，**任何引用成本数字的结论都必须带上"基于占位假设"这句**。
