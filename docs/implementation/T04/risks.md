# T04 · risks — 风险与残留

> 分级：🔴 上线阻断 / 🟡 需关注 / 🟢 已消解（保留记录以免后人重复踩）。
> 每条都写"**为什么**它是风险"与"**什么时候**必须消解"，而不是只贴标签。

---

## 🔴 R1 — 无 pgvector 语义召回：结构化召回对"同义不同词"无效

**状态**：明确不做（用户已确认）。libSQL/Turso 无 pgvector，一期只做
**硬门控 → 结构化过滤 → 词元互补召回 → 解释性排序**。

**具体表现**：两段诉求若表达同一件事但用词不同，**不会互相命中**。
夹具里已能观察到：`"清关"` 与 `"报关"`、`"渠道"` 与 `"通路"` 在词元层面完全不相交。
`tokenize()` 用 CJK 2-gram + 拉丁 ≥3 字符，**没有词表、不做同义归并** —— 这是刻意的
（引入词典会让"换词典即换排序"，破坏 AC-13 要求的固定测试集可复现性）。

**为什么标 🔴**：它是**产品能力**缺口，不是技术债。用户看到的后果是"明明有人能帮我，系统却没推给我"，
而系统无法解释自己漏了什么（因为它根本没有"相似度"的概念）。

**消解时机与方式**：**M6（迁 PostgreSQL + pgvector）**。届时：
- 保留现有结构化管线作为**第一段过滤**（它便宜且可解释）；
- 在其后加语义召回作为**补充候选来源**，并给每条候选标注"来自哪条通路"；
- `explainCandidate()` 必须同步扩展 —— 语义命中的依据是可解释的**近邻片段**，不能退化成一个分数。

**过渡期的产品缓解**：候选页明确写"按双向同时成立来筛选"，让用户理解筛选口径；
无候选时给确定性原因，而不是含糊的"暂无推荐"。

## 🔴 R2 — 隔离仍是应用级，不是数据库级（继承 T01/T02/T03）

**状态**：libSQL 没有 RLS。候选服务的隔离完全靠 `candidates.ts` 里的写法：
所有查询带 `organizationId`，且 `evaluateCandidates` **不导出**（绕开它等于绕开租户隔离）。

**T04 的具体表现**：候选是**第一个会同时读取多名成员数据的读路径** ——
T03 的意图读取基本是"我读我的"，而候选天生要跨用户聚合。因此一次谓词遗漏的
**影响面比 T03 更大**：漏了 `organizationId` 就不再是"看到自己的意图"，
而是"看到别的社群的意图 + 其档案投影"。

**已做的补偿**：
- 服务层入口只接受 `TenantContext`（本身即"已过 `resolveTenant` 成员校验"的类型标记），
  不接受裸的 `{organizationId, userId}` —— 后者会让调用方觉得自己可以随手拼一个；
- 分享令牌入口**二次校验 membership**（令牌只证明"拿到链接"）；
- `tests/connection/candidates.test.ts` 有跨租户 → 404 的用例。

**残余**：编译期无法强制。彻底消除要靠 M6（PostgreSQL + RLS）。

## 🟡 R3 — 披露档位次序是"历史数据语义"的隐式依赖

**状态**：库里 `SocialIntent.disclosure` 存的是档位**名字**（`"CANDIDATE"`），
而理解这些名字的是 `DISCLOSURE_AUDIENCES` 的**数组次序**。

**为什么是风险**：若有人为了"可读性"重排这个数组（例如把 `CANDIDATE` 挪到 `COUNTERPARTY` 前面），
**存量数据的可见性会静默漂移** —— 而且没有任何迁移能修（库里存名字不存序号）。
`field-catalog.test.ts` 的不变量断言会在 CI 阶段拦住，但**改这段代码的人必须先跑测试**。

**消解时机**：M6 迁 PG 时把档位落成**带显式 rank 列的查找表**，把"次序"从代码常量变成数据。

## 🟡 R4 — 候选页的"诉求正文可见"依赖表单上的一句声明

候选能看到对方的 `need` / `offer` 正文（它们**参与匹配**，不给就没法判断要不要连接）。
这是一条**明示取舍**，前提是意图表单上写明了
「我需要/我能提供会展示给同任务的参与者」（`intent-text-visibility`）。

**风险**：这是一条**产品/文案层**的前置，代码层无法强制。
若有人为了"界面简洁"删掉那句声明，用户会在**不知情**的情况下把诉求正文暴露给同任务的候选 ——
`candidates.test.ts` 不会变红（它测的是投影，不是文案）。

**缓解**：`candidates.ts` 文件头把这条前置写成了显式约束：「不得在没有那句声明的情况下上线这条通道」。
**建议**：T12 的端到端门禁里加一条"意图表单存在诉求可见性声明"的断言，把文案也纳入门禁。

## 🟡 R5 — `constraints` 不进候选：是政策，不是技术必然

**选择**：候选只能看到「参与匹配的字段」+「经授权披露的档案字段」。`constraints` **不给**。

**理由**：它是筛选口径（可能含内部判断，例如"不接受独家代理"），且不参与匹配计算。
统一规则比"逐字段争论要不要给"更好审计。

**残余风险**：`constraints` 里可能出现用户**以为会展示**的内容（类似 T03 的 `need`/`offer`），
而它不给候选看。这是**保守方向**的偏差（少给而非多给），不构成越权；
但若产品后续决定"约束也要展示"，**必须先更新披露声明**，再改代码 —— 顺序不能反。

## 🟡 R6 — 候选规模未做压测；`limit` 默认 50

**状态**：`buildCandidates` 在内存里对**该任务下全部意图**做词元化与两两比较：
复杂度 `O(N × L)`（N = 同任务意图数，L = 文本长度）。一期任务规模（几十~几百人）无问题，**未做压测**。

**为什么记下来**：`limit` 是**截断输出**，不是**限制计算量** —— 它作用在排序之后。
任务规模上千时，单次请求的词元化开销会线性上升，而 `limit=10` 一点也帮不上。

**消解时机**：T12（负载与回归测试）时测量；若需要，改为"先粗筛（关键词倒排）再精算"，
或引入缓存。**注意**：加缓存必须同步处理撤销失效（见 T03 `risks.md` R6 的同一条不变量）。

## 🟡 R7 — 分享令牌路径的候选页把 `missionId` 交给服务端换取

公开投影**刻意不含 `missionId`**（内部标识不进 DOM），因此 `/m/<token>/matches`
只能把令牌交给服务端，由服务端换成 mission + 租户后再做成员校验。

**风险**：这条路径**同时**承担"令牌校验"与"成员校验"两件事。
若有人为了性能把 `listCandidatesByShareToken` 改成"只校验令牌"，页面就会对
**任何拿到链接的人**展示全体成员候选 —— 而 `candidates.test.ts` 里
「非成员 → null」那条用例是唯一会变红的断言。

**缓解**：函数文件头写明"令牌只证明拿到链接，不证明是这个社群的人"；
用例断言 `membership.findFirst` **被调用过**，而不只是断言返回 null。

## 🟡 R8 — E2E 依赖本机真实 Chrome 与 dev server，未接 CI

同 T03 R8：`playwright.t02.config.ts` 用 `channel: 'chrome'`（本机 Playwright 自带 chromium
在 macOS 13 不受支持），需要先起 `next dev` 与隔离库。**当前只能在开发机复现**。

**本刀新增的依赖**：T04 的 E2E 还需要**两个**夹具脚本按序跑
（`seed-t02-e2e.mjs --regenerate` → `seed-t04-e2e.mjs`）。
`seed-t04-e2e.mjs` 会显式检查 `mission_e2e_active` 是否存在并在缺失时**报错**，

**消解时机**：接 CI 时统一用 `next build && next start`（生产模式）+ 容器内 chromium。

## 🟢 R9 — 档位次序曾按直觉写反（本刀最危险的一处，已消解并上锁）

**曾发生**：本刀实施中，我最初按直觉认为"候选比对手方更早、更生疏，档位应该更窄"，
准备把 `CANDIDATE` 插在 `ORGANIZER` 与 `COUNTERPARTY` **之间**。

**严格推导后结论相反**：记 `C` = 已同意的对手方集合，`P` = 同任务的互补伙伴集合，
则 **`C ⊆ P`**（任何对手方在同意之前本来就是候选伙伴）→
`{组织者} ∪ C ⊆ {组织者} ∪ P` → **`CANDIDATE` 更宽，必须追加在末尾。**

**若写反的后果**：`rank(granted) >= rank(viewer)` 会让 `rank(COUNTERPARTY) >= rank(CANDIDATE)` 成立
→ **尚未同意的人看到了用户只授权给已同意对手方的字段**。一次**静默的越权披露**：
无报错、无日志、界面正常，只有不该看到的人看到了字段值。

**已消解**（三层，缺一层都不够）：
1. `field-catalog.ts` 顶部写下**完整真相表**（granted × viewer 的 ✓/✗ 矩阵），把关键一格显式写出；
2. `field-catalog.test.ts` 加**次序不变量**断言；
3. `candidates.test.ts` 加**变异自证**：把候选投影换成 `COUNTERPARTY`，`age` 必须漏出来。

> 教训：**"更具体的受众"感觉更窄，但集合关系上是更宽** —— 直觉在单调性问题上不可靠，必须写推导。

## 🟢 R10 — E2E 首跑失败曾被误认为鉴权故障（已消解）

**曾发生**：`candidate-match.spec.ts` 首跑 **2 passed / 1 failed**，失败断言是
「登录后 `session-token` 必须存在」→ false，而**同一文件的后一个用例却通过了**。

**真因**：`beforeAll` 漏了 `/api/auth/login` 预热。dev 下该端点首访要现场冷编译，
3 次登录重试全落在编译窗口内。

**为什么危险**：症状指向"鉴权坏了"，且**后续用例又好了** —— 极易被判为随机抖动，
进而用"加重试次数"掩盖（那会让问题藏得更深）。

**已消解**：补上预热后 3/3 通过。已把这条写进 `tests.md` §7.3 与 spec 的注释里。

## 🟢 R11 — 候选页原本会暴露 `missionId`（未发生，设计阶段规避）

公开投影不含 `missionId`，本可以在页面上"顺手"把它渲染成 `data-mission-id` 供前端调用 API。
**没有这么做**：页面用**纯 RSC**，服务端直接拿到数据，前端不需要 `missionId`。

`missionId` 只在 E2E 里由夹具显式提供（`E2E_MISSION_ID`），因为测试需要直连 API 取证。
这条边界属于"内部标识不进 DOM"的一部分，与 T02/T03 同口径。
