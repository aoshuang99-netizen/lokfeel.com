## 1. 🔴 本轮最有价值的一次发现：示例差点是**不可运行**的

第一版我把凭据写成 `LOKFEEL_TOKEN`，并以 `Authorization: Bearer <token>` 发送。
看起来很像一个正常的 SDK 示例。**跑一次就会 401** —— 因为：

```
requireAuth()  →  NextAuth auth()  →  会话 cookie
```

代码里**不存在**读 `Authorization: Bearer …` 的分支。也就是说，那个示例
"看起来专业、实际只会拿到 401"，而它正是要交付给外部开发者照抄的东西。

**T11 的铁律第一条就是「外部示例可运行」。** 一个跑不通的示例，比没有示例更糟：
外部开发者会先怀疑自己的环境，再怀疑文档，最后放弃集成。

### 修法：示例与浏览器**同形**

```
① LOKFEEL_COOKIE            → 直接给会话 Cookie 头值（CI / 已登录的浏览器里复制）
② LOKFEEL_LOGIN_EMAIL/PASSWORD → 示例自己 POST /api/auth/login，读 Set-Cookie 后复用
③ 都没有                     → 只有 demo-discovery.ts 能跑（它本来就全部基于"无凭据"）
```

同时把**没有 Bearer 入口**这件事写进了 `lokfeel-client.ts` 文件头与 README：

> 若将来需要长期有效的机器令牌（无头集成），那是一条**新的认证能力**
> （签发 / 轮换 / 吊销 / 作用域），必须单独评审，不该混在"示例"这一层悄悄加。

**为什么不顺手加一个 Bearer 支持？** 因为那是往认证面上开一条新路径 ——
它需要令牌签发、轮换、吊销、作用域、以及"令牌泄漏了怎么办"的答案。
为了"让示例好看一点"而引入这些，方向反了。

### 从这次发现里抽出的通用规则

> **示例里出现的每一个机制，都必须在真实代码里存在。**
> 写示例时最容易犯的错不是"写得不够漂亮"，而是**发明一个不存在的东西**
> ——一个头、一个参数、一个状态码。它读起来自洽，跑起来 401。
> 判据：示例的每一行都应当能对应到服务端的一段代码；对不上，就先证明了再写。

## 2. 为什么示例要带**断言**，而不只是打印 JSON

演示脚本只有两种结局：**通过，或明确地失败**。一个只打印 JSON、永远 `exit 0`
的示例，放进 CI 等于没跑；而"越权必须失败"这类**安全命题**，恰恰需要示例自己
把结论说出来，而不是让读者自己看输出判断。

所以 `expect.ts` 提供三态：

| 态 | 含义 | 用于 |
|---|---|---|
| `✓ ok` | 断言成立 | 正常路径 |
| `✗ FAIL` | 断言失败 ⇒ `exit 1` | 任何可判定的命题 |
| `~ SKIP` | **无法确定**，显式说出来 | 见 §3 |

> 一条恒真的断言等于没有断言。所以示例里**不写**"服务端会记录日志（本示例读不到，
> 仅提示人工核验）"这类永远为真的检查 —— 它降级成一行提示文字，不占断言位。

---

## 3. `SKIP`：为什么"夹具不适用"必须显式说出来

越权演示需要调用者的角色**恰好不具备**目标能力：

- `mission.read` ⇒ OPERATOR 及以上才有；
- `bridge.manage` ⇒ ADMIN 及以上才有。

若读者用一个高权限账号跑，这几条**无法**成立。此时只有两种诚实做法：

1. 打印 `SKIP` 并说明原因（本次选择）；
2. 让断言直接失败 —— 但那是**假失败**，会让人以为功能坏了。

**最坏的做法是静默算通过**：它把"越权被拒"这条结论变成一句**无证据的声明**。
所以 `SKIP` 不是"宽松"，而是**把不确定显式化**——它和 `FAIL` 一样是信息，
而不是通过。

## 4. 示例为什么必须进 `tsc`

`tsconfig.json` 的 `include` 是 `**/*.ts`，`exclude` 里**没有** `examples/`
—— 也就是说 `npx tsc --noEmit` 会**一并检查**示例。

这是**刻意保留**的：

- 反面做法是把 `examples/` 加进 `exclude`，示例就不会因为类型错误而报红；
- 但那样示例就成了 markdown 的近亲 —— **只在有人真的去跑它的时候才会发现坏了**，
  而那时它已经作为"文档"发布出去了。

`tsx` 用 esbuild 剥类型**不做类型检查**，所以"能跑"和"类型正确"是两件事，
必须分别验（本次两件事都做了：`tsc` exit 0 + 端到端实跑 exit 0）。

## 5. 三组"授权 vs 越权"的对照设计

每个示例内部都成对：**只演示"能调通"证明不了任何安全属性**（把守卫删掉，
那个演示依然通过）。所以每组的越权那一半都**必须断言为失败**：

| 示例 | 授权（正） | 越权（负） |
|---|---|---|
| `demo-mcp.ts` | `list_bridges`（`bridge.read`）成功 | ① 无会话 ⇒ 401；② `list_missions` 能力不足 ⇒ `isError:true`；③ 未知工具 ⇒ `-32602` + `available`；④ 未实现方法 ⇒ `-32601` / 404 |
| `demo-a2a.ts` | `list_bridges` ⇒ `completed` | ① 无会话 ⇒ 401；② 能力不足 ⇒ 200 + `failed` 且 `artifacts` 为空；③ 未知技能 ⇒ 404；④ 缺 `skillId` ⇒ 400 |
| `demo-rest.ts` | `GET /api/v1/bridges` ⇒ 200 | ① 无会话 ⇒ 401；② 匿名 `POST` ⇒ **401 而非 400**（守卫先于请求体校验）；③ `POST` 能力不足 ⇒ 403 |

`demo-rest.ts` 里还有一条**演示脚本不该有副作用**的处理：`POST /api/v1/bridges`
刻意**不传** `Idempotency-Key`。于是一个高权限账号（能过 `bridge.manage` 门槛）
也只会拿到 `400`（缺幂等键），而**不会真的建出一份协议**。

## 7. 未覆盖 / 诚实声明

1. **`examples/sdk` 不是发布级 SDK**：不发布到 npm、不承诺语义化版本、没有
   `package.json` / 构建产物。它是**可运行的文档**。
2. **示例的"协作"全部是只读操作**：写工具（`report_outcome`）需要真实 `proposalId`，
   在没有完整 T05 链路的隔离库里只能得到 400。因此不虚报写入链路已端到端打通。
3. **`login()` 使用邮箱 + 密码**：这是把"人的操作"脚本化。它适合开发/CI，
   **不适合**长期运行的集成 —— 那种场景真正需要的是机器令牌（见 §1）。
4. **没有 Node 之外的示例语言**：用户拍板 TypeScript / Node；Python / Go 示例未提供。
