# T01 · risks — 风险清单

> 按「已发生 / 已规避 / 未消除 / 需决策」四类。**未消除的风险不假装消除。**

---

## 1. 未消除的风险（需知晓）

### R1 🔴 隔离目前是「应用级强制」，不是「DB 级强制」

| 项 | 说明 |
|---|---|
| 现状 | `resolveTenant()` + 查询谓词 + 负测构成应用级强制；**无 RLS** |
| 原因 | 现网是 libSQL/Turso，**该引擎没有行级安全**（`DIALECT-DIFF.md` D7） |
| 影响 | 若某处代码**忘记**带 `organizationId` 谓词，DB 不会拦住，只能靠 code review 与测试发现 |
| 缓解 | ① 已有「查询必须带 userId+organizationId」防回归锁；② M6 上 PG 后启用 RLS 作为第二道 |
| 消除路径 | M6（与 PG 搬迁同批） |

> 这是 T01 最重要的**残留风险**。契约 `schema.sql:64` 要求 RLS，当前只能算「等价应用层强制」。

### R2 🟠 30 个 JSON 字段仍是 `String`，未迁 `jsonb`

| 项 | 说明 |
|---|---|
| 现状 | 保持原样（**有意不改**，见 `DIALECT-DIFF.md` §3.2） |
| 原因 | 批量改列类型必须与读写两侧 codec 收敛同批，否则会出现「有的存字符串、有的存对象」的静默腐化 |
| 影响 | 迁移后仍是「JSON 存在文本列」，无法用 `jsonb` 索引/查询 |
| 消除路径 | M6 后独立批次（L3 层） |

### R3 🟠 `provider` 未切换，schema 与实际运行方言仍有「名义差」

| 项 | 说明 |
|---|---|
| 现状 | `datasource.provider = "sqlite"` 保持不变，PG 兼容性只在文档层就绪 |
| 影响 | 用户决策的「迁 PostgreSQL」目前**只完成到「可迁移」而非「已迁移」** |
| 消除路径 | M6；前置是 PG 实例 + 停机窗口 + 双写方案确认 |

### R4 🟡 业务路由尚未接入 `withTenant()`

| 项 | 说明 |
|---|---|
| 现状 | `src/lib/tenancy/**` **零引用**（运行时行为与改造前逐字一致） |
| 双面性 | ✅ 零回归风险；⚠️ 但也意味着**租户隔离目前对真实流量尚未生效** |
| 消除路径 | T02 起，首个租户作用域接口（`/api/v1/missions`）接入，并补 HTTP 层 E2E |

## 2. 已消除 / 已规避的风险

### R5 ✅ 迁移对既有查询的破坏 → 已规避

全部走「加列优先」：新增列**可空**、三张新表独立、无既有表结构变更。
生产实测：迁移后 `/api/health` 200 healthy、`/api/geo-check` 200。

### R6 ✅ 迁移不可重跑 → 已规避

`migrate.mjs` 先查 `PRAGMA table_info` 再决定是否加列；M2 用 `WHERE ... IS NULL`。
本地实测：二次执行全部 `⏭ 跳过`、回填 0 行。

### R7 ✅ `prisma db push` 对远程 Turso 失败（P1013）→ 已规避

迁移脚本走 `@libsql/client` 直执行 SQL，完全不依赖 `db push`；`prisma/migrations/` 仅作变更记录。

## 3. 已发生的缺陷（已修复，留档）

| # | 缺陷 | 发现方式 | 修复 |
|---|---|---|---|
| B1 | `migrate.mjs` 把「表不存在」误判为「已存在」（`PRAGMA` 返回空集是 truthy） | 首轮 probe 输出与实际矛盾 | `tableColumns` 改为空集 → `null` |
| B2 | `outcome.verify` 已声明但未分配给任何角色 | 单测「OWNER 覆盖全部能力」失败 | 归入 `ADMIN_EXTRA`；加结构性守卫断言 |
| B3 | `--to-schema-datamodel` 在 Prisma 7 已移除 | 生成基线 DDL 时报错 | 改用 `--to-schema`；同步文档 |
