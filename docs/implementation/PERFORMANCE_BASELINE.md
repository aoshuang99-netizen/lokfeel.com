## 1. 方法（先说清「测的是什么」，否则数字没有意义）

| 决策 | 取值 | 理由 |
|---|---|---|
| **打哪里** | **本地构建产物**，非生产 | 生产是跨境 Netlify 共享 serverless：测出来的是**网络抖动与平台限流**，不是本仓代码成本；且对生产开并发**本身就是攻击**。 |
| **依赖** | **零新增**（Node 22 自带 `fetch`） | 不引 autocannon / k6 / artillery —— 本仓正被依赖高危困扰（见 `DEPENDENCY_RISK.md`），多一个依赖就多一条供应链风险与版本漂移。 |
| **打什么路径** | 只打**读**与**被拒（401）**路径 | 压测若写库，就把「性能」与「数据污染」耦在一起。全部请求匿名可复现、零副作用。 |
| **延迟口径** | `fetch` 发起 → **响应体读完** | 不读完就计时会漏掉传输与反序列化成本，那是自欺。 |
| **数据隔离** | `DATABASE_URL=file:./perf-baseline.db` | 见 §2 的安全实证。 |
| **重复次数** | 每档 **3 次**，取**中位数**，**保留 3 次原始值** | 见 §3 的噪声讨论。只报聚合值会把「不可重复」藏起来。 |

## 3. 实测基线

**环境**：`Intel Core m3-7Y32 @ 1.10GHz`（**4 核 / 8GB / 无风扇超低压 U**）· macOS `darwin 22.6.0` · Node `v22.22.2`
· 每档 10s × 3 次取中位数 · 暖机 3s · `redis=memory`（未配 Upstash，走降级路径）

### 3.1 延迟 p95（毫秒，三次中位数）

| 端点 | c=1 | c=10 | c=50 | SLO 阈值(c=1 / c=10 / c=50) |
|---|---|---|---|---|
| `health` | 20.01 | 63.07 | 370.88 | 150 / 300 / 900 |
| `org-anon` | 16.44 | 113.20 | 465.14 | 同上（Tier A） |
| `members-anon` | 17.03 | 104.74 | 497.51 | 同上 |
| `mcp-discover` | 13.97 | 91.94 | 415.22 | 同上 |
| `mcp-call-anon` | 19.92 | 123.79 | 570.75 | 同上 |
| `a2a-anon` | 17.06 | 111.29 | 523.83 | 同上 |
| `home` | 24.82 | 174.13 | 690.48 | 800 / 1200 / 3000（Tier B） |
| `login` | 65.04 | 498.92 | **2569.79** | 800 / 1200 / 3000 |

**错误率**：三档全部 **0.00%**（0 个非预期状态码、0 个连接失败）。
**吞吐**：c=1 → 84 rps；c=10 → 109 rps；c=50 → **99 rps**（不升反降 ⇒ 已饱和，见 §4）。
**总断言**：`npm run check:slo` → **48/48 通过**。

### 3.2 三个真实观察

**① `login` 是最重的端点，且随并发恶化最快**（65 → 499 → 2570 ms，c=1→50 放大 40 倍）。
而 `home` 只放大 28 倍、`health` 18 倍。⇒ 登录页的 SSR 路径是**本仓最贵的同步渲染**，值得单独看一眼（但不属 AC-24 的修复范围）。

**② 吞吐在 ~100 rps 饱和。** c=10 的 109 rps 已是上限，c=50 反而降到 99 —— 继续加并发只是把延迟推高，不换来吞吐。

**③ 单次测量不可靠 —— 这是本轮最重要的方法论修正。**
首轮**单次**运行时 `login@50` 的 p95 是 **3044ms**，**超过 3s 阈值**（看起来像 SLO 失败）。
改用「3 次取中位数」后三次原始值为 **1995 / 2569 / 2757 ms**，中位数 2570ms，**通过**。
⇒ 那个 3044ms 是**离群值**。**若当初直接拿单次数字判 PASS/FAIL，就会在噪声上下结论。**
基线里每个端点的 `p95Spread`（各次区间）被完整保留，就是为了让这个噪声**可见、可复核**：

| 端点 @ c=50 | p95 三次区间 | 相对跨度 |
|---|---|---|
| `login` | 1995.62 ~ 2757.45 | 38% |
| `mcp-call-anon` | 415.40 ~ 723.00 | 74% |
| `mcp-discover` | 270.56 ~ 485.92 | 80% |
| `health` | 263.61 ~ 414.31 | 57% |

> ⚠️ **c=50 档的置信度明显低于 c=1 / c=10**（跨度 38%~80%）。任何基于 c=50 的精细判断都应先看 `p95Spread` 再下结论。

### 3.3 SLO 定义（`docs/implementation/slo.json`）

阈值按**两档分级 + 三个并发档位**表达：

| 层级 | 端点 | c=1 | c=10 | c=50 | 依据 |
|---|---|---|---|---|---|
| **A**（交互式 API） | health / 三个 401 / mcp / a2a | ≤150ms | ≤300ms | ≤900ms | 同步等待路径；业界经验：≤100ms 感觉即时，≤300ms 可接受 |
| **B**（SSR 页面） | home / login | ≤800ms | ≤1200ms | ≤3000ms | 首屏含 RSC 组装与 HTML 传输，可接受窗口明显更宽 |
| 错误率 | 所有端点 | ≤0.5% | ≤1% | ≤3% | 1% 是「不构成用户可见故障」的分界 |

**两条方法论约束（写进文件、也写进脚本注释）**：

1. **阈值按 UX 可接受度先行确定（绝对毫秒数），再跑实测验证** ——
   **不按实测值反推阈值**。按实测反推会让 SLO 永远达标，等价于没有 SLO。
2. **负载越高排队越久是物理必然** —— SLO 表达的是「**该档位下的上界**」，而不是要求「延迟不随负载变化」。

## 5. T11 交接项：MCP / A2A 的速率限制缺口 —— **已证实 → 已修复**

> **状态（2026-10-17）**：本节是**修复前**的取证与定性，**保留原样作为证据**，不要按现状阅读。
> 修复内容见 `BACKLOG.md` §7quinquies：① 桶键改 `ratelimit:<name>:<rateKey>`、`name` 必填且同名不同额度注册期抛错；
> ② `/api/mcp` 与 `/api/v1/a2a/tasks` 各接 120 次/分钟/IP 的独立桶。
> `scripts/perf/rate-limit-probe.mjs` 的判定已**反转**：现在「打到超额度却看不到 429」才判失败；
> 需要对旧构建复现本节结论时加 `--expect=gap`。
> `perf-rate-limit.json` 是修复前的快照，**故意不重新生成**（否则历史证据被覆盖）。
>
> **生产实证（2026-10-17，部署 `6ad307fdf48e`）**：并发探针（`--concurrency=20`）130 次 →
> 对照 `404×120 + 429×10` · MCP `200×120 + 429×10`（9.8s）· A2A `401×120 + 429×10`（9.6s），
> 结果见 `perf-rate-limit-after-fix.json`。
> ⚠️ **本探针必须并发突发**：串行的 130 次要 160s，超过 MCP 的 60s 窗口 ⇒ 窗口中途重置 ⇒
> 每个窗口只装到约 50 次、永远打不满 ⇒ 会把"探针太慢"误报成"限流缺失"（本轮真的踩到了）。
> 现在脚本对 `wallMs ≥ windowMs` 的目标直接判「**取证不合格**」，并在措辞上与「回归」区分开。

### 5.1 结论：**无速率限制，且带阳性对照**（修复前）

取证脚本 `scripts/perf/rate-limit-probe.mjs`（`docs/implementation/perf-rate-limit.json`）：

| 目标 | 请求数 | 状态分布 | 429 |
|---|---|---|---|
| **对照** `GET /api/v1/public/missions/<token>`（配置 120 次 / 5 分钟 / IP） | 130 | `404×120` + `429×10` | **10** |
| `POST /api/mcp`（`tools/list`，公开发现面） | 200 | `200×200` | **0** |
| `POST /api/v1/a2a/tasks` | 200 | `401×200` | **0** |

**为什么这个「0」可信 —— 阳性对照**：
对照端点打出**恰好 10 次 429**（前 120 次通过、后 10 次被拦），与它配置的 `max: 120` **完全吻合**。
⇒ 探针**有能力**看见 429 ⇒ MCP/A2A 的「0 次 429」不是探针瞎了，而是**真的没有限流**。

脚本把这条纪律写死为**硬判据**：若对照端点一次 429 都没出现，脚本**判失败并声明「本次取证不合格，不能结论」**，
而不是含糊地报一句「没有限流」。

### 5.2 🔴 顺带发现的**新缺陷**：三个限流器**共用一个 per-IP 桶**（已修，见 §5 顶部状态）

在核对「谁有限流、谁没有」时，读到了 `src/lib/rate-limit.ts` 的取键逻辑：

```ts
const ip = request.headers.get('x-forwarded-for')?.split(',')[0] || ... || 'anonymous'
const rateKey = options.key ? options.key(request) : ip     // ← 未传 key 时只用 IP
const redisKey = `ratelimit:${rateKey}`                     // ← 没有路由/功能维度
```

而本仓三处调用，**没有一处传 `key`**：

| 调用点 | 配置 | 实际 key | 是否落在 IP 命名空间 |
|---|---|---|---|
| `previewLimit`（missions 预览） | 120 次 / 5 min | IP | ✅ |
| `joinLimit`（missions 加入） | 30 次 / 5 min | `u:<userId>`（构造了合成请求） | ❌ 独立命名空间 |
| `callSignalLimiter`（WebRTC 信令） | 300 次 / 1 min | IP | ✅ |

**后果（`previewLimit` 与 `callSignalLimiter` 共用 `ratelimit:<ip>`）**：

1. **计数共享**：一次通话产生的信令（可达 300 次/分钟）会计入 missions 预览的 120 次/5 分钟额度，反之亦然。
2. **窗口由「最先创建该条目的那次请求」决定**（in-memory 分支保留原 `resetAt`）：
   - 若预览请求先建条目（5 分钟窗），则信令的「300 次/分钟」实际变成「**300 次/5 分钟**」= 1 次/秒 ——
     **可能影响长通话的信令节奏**；
   - 若信令先建条目（1 分钟窗），则预览的「5 分钟」实际只持续 1 分钟 —— 限流被**削弱**。

**定性**：这是**跨功能干扰**，不是安全绕过 —— 但两个方向的后果都不好（一个可能伤实时通话，一个削弱匿名面防护）。

**⚠️ 诚实边界**：本条是**代码级**结论。运行期复现需要「**同一 IP 上同时使用两个功能的已登录会话**」，
本次**没有**这样的会话 ⇒ **未做运行期实证**。已按此如实登记，**不冒充实测**。

**处置**：**不在本轮修**。理由与 AC-23 不改迁移脚本一致 —— 改 `rate-limit` 的取键会**改变生产流量的限流语义**，
应作为一个**独立变更**，带自己的测试与生产复验，而不是塞进「性能基线」这一轮。
已记入 `BACKLOG.md`（P1），并给出修复要点：**每个限流器显式传 `key`**（如 `` key: (req) => `missions-preview:${clientIp(req)}` ``）。

## 6. 与 CI 的关系：**为什么性能不做 push 门禁**

这是本轮第二个关键取舍，沿用 AC-23 的教训（**「恒红的门禁比没有门禁更危险」**）：

| 动作 | 是否进 CI | 为什么 |
|---|---|---|
| **SLO ↔ 基线 对账**（`slo-check.mjs`） | ✅ **进**，push/PR 触发（job `slo-check`） | **确定性**：只读两个冻结 JSON。谁把 `slo.json` 改成与基线矛盾、或删掉基线，立刻判红。**零抖动、零成本**（纯 Node 标准库，不需要 `npm ci`，十几秒）。 |
| **实跑压测**（`perf-baseline` job） | ⚠️ **仅手动**（`workflow_dispatch`） | 共享 runner 上延迟抖动极大（§3.2 显示同档位跨度可达 80%）。给延迟挂硬阈值 = 随机变红 = 把「红」这个信号贬值。压测是**取证动作**，不是**门禁动作**：产出 artifact，人工复核后再更新基线。 |

`slo-check` 的**自证**（`npm run verify:check:slo`，6/6 通过）同时含两个方向，缺一不可：

- **判红有牙齿**：篡改 p95 超标 → 红 ✓ · 篡改错误率超标 → 红 ✓ · 删除整档数据 → 红 ✓ · 基线非法 → 红 ✓
- **不是恒红**：阈值放宽到无穷 → 必须**通过** ✓

> 只证前者会得到一个永远红的校验器 —— 那比没有校验器更糟。
