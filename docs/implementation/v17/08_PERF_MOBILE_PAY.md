# 08 · 首屏性能与移动端支付

**产出**：2026-10-21 · WB17-08
**基线**：`e281e51`
**采集器**：`scripts/perf/measure-vitals.mjs`（`npm run perf:vitals` · 自证 `npm run verify:perf:vitals`）
**原始数据**：`docs/implementation/v17/performance/vitals-production.json`（3 页 × 3 轮，逐轮留档）

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 移动端首屏能过 Core Web Vitals 吗 | **不能。** 3 个公开页全部 WARN（0 PASS / 3 WARN / 0 FAIL） |
| 最差的是哪一页 | 首页：LCP 中位 **3388ms**，**首访（冷）6284ms** |
| 瓶颈是图片吗 | **不是。** 三页的 LCP 元素**全是 `H1`**，图片传输 **0KB** |
| 瓶颈是什么 | **TTFB + 首屏 JS 执行**。TTFB 占 LCP 的 42%–68%，剩下的主要是 267–291KB JS |
| 移动端支付能用吗 | 落地页可用（LCP 1884ms PASS），但**真正的结账不在我们站内** —— 它跳去 Gumroad，而 Gumroad 在大陆不可达 |
| 触控目标合格吗 | **不合格**。首页 13/18、登录页 26/31 个可交互元素低于 24px 高（WCAG 2.5.8 AA 要求 24，Apple HIG 要求 44） |

一句话：**这不是"性能需要优化"，是"首访者在 4G 上要盯 6.3 秒白屏"。**

## 1. 方法（为什么这个数可以信）

```
Chromium（headless）
· 视口 390×844 · DPR 3 · isMobile · hasTouch · iPhone UA
· 网络 4G 档：150ms RTT / 1.6Mbps 下行 / 750kbps 上行
· CPU 4× 降速（移动中端机的执行能力，不是桌面机）
· 每页 3 轮，每轮**新上下文**（缓存必然冷，不靠"第二轮变快"美化）
· 指标全部取自 Performance API：LCP / FCP / CLS / TTFB / transferSize
```

三条口径约定，缺一条数就会骗人：

1. **中位数取 3 轮，冷启动单列。** 首轮 LCP 6284ms 与中位 3388ms 是两件事：
   前者是"第一个访客等多久"，后者是"再来一个人等多久"。混在一起算平均，两边都失真。
2. **LCP 等网络安静后再读，不等固定 sleep。** 否则读到的可能是还在涨的中间值。
3. **采不到数就 `NO_DATA`，不拿 0 顶替** —— 0 会被判成"极快"，那是负负得正。

自证 7 条（`npm run verify:perf:vitals`），核心是三个反向对照：

| 对照 | 期望 | 实测 |
|---|---|---|
| 本地"快"页面 | PASS（证明不是恒红） | PASS · LCP 104ms |
| 本地"慢"页面（服务端延迟 3600ms） | FAIL（证明检测器有牙齿） | FAIL · LCP 3640ms |
| 空白页（无任何内容） | NO_DATA/FAIL（不许拿 0 冒充） | NO_DATA · LCP null |
| 连不上的地址 | FAIL（不许静默跳过） | FAIL |
| 20px / 48px 按钮 | 前者违规、后者不误报 | 1 违规 / 2 总数 |

|---|---|---|---|---|---|---|---|---|
| `/`（落地页） | WARN | **3388ms** | **6284ms** | 3388 | 1435 | 0.001 | 267KB | 433KB |
| `/pay.html`（付款页） | WARN | 1884ms | 2584ms | 1884 | 1290 | 0.001 | **11KB** | **14KB** |
| `/login` | WARN | 2992ms | 3740ms | 2992 | 1483 | 0.001 | 291KB | 753KB |

分项（阈值：LCP 2500/4000 · TTFB 800/1800 · CLS 0.1/0.25 · JS 300/600）：

| 页面 | LCP | TTFB | CLS | JS |
|---|---|---|---|---|
| `/` | WARN | WARN | PASS | PASS |

## 3. 三个能解释的现象（这才是本轮真正的收获）

### 3.1 TTFB 吃掉 LCP 的 42%–68%，而且它是平台给的

| 页面 | TTFB / LCP | 占比 |
|---|---|---|
| `/` | 1435 / 3388 | 42% |
| `/login` | 1483 / 2992 | 50% |
| `/pay.html` | 1290 / 1884 | **68%** |

`pay.html` 是**纯静态文件**（3 个资源、11KB JS），它的 TTFB 仍然 1.29s。
这说明 **1.3s 是这条链路的底座**（Netlify edge + 跨境 RTT + 冷启），与我们的代码无关。

推论：把 LCP 从 3388 压到 2500 以内，**只靠删代码做不到** —— 光 TTFB 就占了一半预算。
真要进 2500，必须动平台（见 §6）。

### 3.2 同域名天然对照：JS 267KB vs 11KB，LCP 差 1.5 秒

这是同一台服务器、同一档网络、同一轮实验里的两组数：

| | 首屏 JS | TTFB | FCP − TTFB | LCP |
|---|---|---|---|---|
| `/pay.html` | 11KB | 1290ms | **594ms** | 1884ms |
| `/` | 267KB | 1435ms | **1573ms** | 3388ms |
| `/login` | 291KB | 1483ms | **1225ms** | 2992ms |

TTFB 差 145ms，但 FCP 到 LCP 的"渲染前耗时"差了 **979ms**（1573 − 594）。
**差值不是服务器造成的，是 JS 造成的** —— 267KB 在 1.6Mbps 下光下载就 1.3s，
再叠加 4× CPU 降速的解析执行。

所以首页的 3.4s 大致是这样构成的：

```
1.4s  TTFB（平台）
2.0s  JS 下载 + 解析 + 执行 + 首次绘制
─────
3.4s  LCP
```

### 3.3 LCP 元素是 `H1`，图片传输 0KB

三页的 `lcpEl` 全是 `H1`，`imgBytes` 全是 **0**。
这直接推翻了一条常见的优化直觉：**本项目首屏没有图片瓶颈**，
去换 WebP、加 `fetchpriority`、上 CDN 图片，对 LCP 的收益接近于零。

V16 曾把落地页 LCP 从 7008ms 压到 4280ms（推迟 rAF 到 idle、WebP 228→65KB），
那次是有效的 —— 但它动的是"绘制时机"，不是"图片体积"。
本轮的数字说明：**下一步的杠杆在 JS 体积与 TTFB，不在图。**

## 4. 移动端触控目标：24px 与 44px 是两条线

| 页面 | 可交互元素 | < 44px | 比例 |
|---|---|---|---|
| `/` | 18 | 13 | 72% |
| `/pay.html` | 6 | 1 | 17% |
| `/login` | 31 | 26 | 84% |

最小的几个（真实值，单位 CSS px）：

```
/        a "Log in"          35×16
         a "Console"         46×16
         a "Create account"  89×16
/login   a "FAQ"             26×16
         a "Blog"            26×16
         a "DMCA"            38×16
/pay.html a "Apply to yearly" 117×17
```

两个阈值都要说清楚，否则就是拿标准吓人：

- **WCAG 2.2 SC 2.5.8（AA）要求 24×24**，且有例外（行内文字链、间距足够、UA 默认控件）。
  这里 16px 高的独立导航链**不在例外内** ⇒ 24px 也不达标。
- **Apple HIG / Material 建议 44×44 或 48×48**，属可用性建议而非合规要求。
  按这条算，首页 72% 不达标。

**一处自我纠正**：`/login` 报出的 `input 16×16` 大概率是复选框 ——
复选框的**可点区域**由 label 扩展，只量 `<input>` 本身会误报。
所以 26 这个数里有 1 个是**测量方法造成的假阳性**，真实缺陷是 25 个。
我没有把它从表里删掉（删掉就看不见方法缺陷了），而是把结论写成"25 个 + 1 个误报"。

## 5. 移动端支付：真正的承载方不在我们站内

这一节是本轮最不舒服、也最该写下来的部分。

### 5.1 `pay.html` 卖的不是 LokFeel

`/pricing` `/plans` `/subscribe` `/membership` `/pass` 全部 **307 → `/pay.html`**。
打开这个页面，标题是 **"Hlua Pass — Choose your plan"**，内容是：

- 三个套餐：Binge $12.99/月 · Inner Circle $99.99/年 · Insider $32.99/季
- 权益写的是"Unlimited streaming of the full library"、"120 H-Points"、"Founder badge"
- 所有 CTA 指向 `shuangster00.gumroad.com/l/hlua-pass-*`

也就是说：**用户点"定价"，会被送到一个卖"内容库订阅"的第三方页面**，
与 LokFeel（Connection OS / 工作区 / Agent 协作）几乎是两个产品。
这不是文案问题，是**产品身份在收钱这一步断裂**。

### 5.2 退款窗口冲突在这一页是硬证据

`pay.html` 第 167 行原文：

> 7-day refund policy on every Pass — request a refund of your latest cycle within 7 days of the charge.

而 `/refunds`（HTTP 200）写的是 **14 天**。两处同时在线，都是用户能看到的。
`BIZ-02` 记的就是这件事；这里补上"它在付款页上，不在某个角落"这一事实。

临时仲裁仍是**宽者优先 = 14 天**（单方面收紧属不利变更）。

### 5.3 移动端支付的"技术风险"其实已经被转移了

`pay.html` 里 **0 个 `<input>`** —— 它不是表单，是一组跳转链接。
所以移动端支付常见的那些坑（键盘顶起、`inputmode` 缺失、金额输入格式化、
信用卡 autofill、双提交）**在本站根本不存在**，因为**收款动作发生在 Gumroad**。

换成三条真的风险：

| 风险 | 现状 | 能不能验 |
|---|---|---|
| 跳转后能不能到达 | Gumroad 在大陆 **DNS 污染 + 12s 超时**（`03` 已记） | 已验：不可达 |
| 跳转后显示的价格是否与站内一致 | 站内 $12.99/99.99/32.99；Gumroad 侧价格**未核** | 无法验（需 Gumroad 账号） |
| 用户付完钱能不能回来 | 无回跳域名白名单验证；`return_url` 未配置 | **未验** |

第三条是移动端支付最容易被忽略的一条：**在手机浏览器里跳走再回来，会话常常已经断了**。
本项目为此专门有 `public-origin.ts` 与 `verify:public-origin`（13 断言）——
但那验的是**站内**跳转，不覆盖"离开本站去 Gumroad 再回来"。

## 6. 结论：该做什么、以及明确**不**做什么

### 该做（按性价比排序）

| # | 动作 | 预期收益 | 成本 | 依据 |
|---|---|---|---|---|
| 1 | 导航链接补最小点击区（`min-height: 24px`，视觉不变，用 padding 撑） | 触控目标 24px 达标；无障碍从"不达标"变"达标" | ~1h | §4 |
| 2 | 修 `/pricing` 的产品身份（不要跳到卖别的产品的页） | 漏斗少一次"这是同一个产品吗"的困惑 | 半天 | §5.1 |
| 3 | 统一退款窗口为 14 天（改 `pay.html` 一处文案） | 关掉 BIZ-02 的一半 | 10min | §5.2 |
| 4 | 首屏 JS 减重（落地页 267KB → 目标 < 150KB） | FCP−TTFB 从 1573ms 降到 ~900ms，LCP 有望进 2.5s | 1–3 天 | §3.2 |
| 5 | 平台侧预热 / 升级（`05` §8 第 1 条） | 冷启 TTFB 3895→~1400，首访 LCP 6284→~3800 | 花钱 | §3.1 |

### **不**该做（这几件事看起来像优化，在本项目上无效）

- ❌ **图片优化**（WebP/AVIF/`fetchpriority`）：`imgBytes = 0`，LCP 元素是 `H1`。收益为零。
- ❌ **加骨架屏**：CLS 已经是 0.001，布局不抖；骨架屏只会再加一段 JS。
- ❌ **预连接 Gumroad**：大陆 DNS 污染，连不上，`preconnect` 只会拖慢首屏。
- ❌ **为 LCP 单独加一个"轻量落地页"分支**：那会让"用户看到的首页"和"产品实际的首页"分叉，
  是拿一致性换指标，本项目的定位（Connection OS）经不起这个。

## 7. 没验的部分（BLOCKED，不用估算代替）

| 项 | 为什么没验 | 解除条件 |
|---|---|---|
| 十三屏（工作区/控制台）的 LCP | 全部需要登录态，生产无 QA 账号 | 允许建生产测试账号 |
| 真实 4G / 真实设备 | 只有 Chromium 模拟档位；无真机 | 有设备，或接 WebPageTest |
| 跳去 Gumroad 再回跳后会话是否保留 | 需 Gumroad 账号 + 一次真实结账 | 支付凭据 + 一笔可退小额交易 |
| 首屏 JS 减重后的复测 | 依赖 §6 第 4 条先实施 | 实施后跑 `npm run perf:vitals` 对比 |

**因此 `UX-08` 仍是 BLOCKED**：它判的是"十三屏在移动端不溢出且可操作"，
本轮验的是三个公开页（且只验了溢出与触控，没验操作路径）。
