# 09 · 第一个客户的 Playbook

**产出**：2026-10-21 · WB17-09
**基线**：`5aa4212`
**状态**：**未演练**。本文所有步骤都**没有**对真实客户跑过 —— 项目当前 0 客户、0 真实交易。
它是一份"到时候照这个做"的预案，不是"我们做过"的记录。这两者的区别，就是本文件存在的理由。

## 0. 效力边界（先说清楚它不是什么）

| 它不是 | 为什么 |
|---|---|
| 不是 SLA | 1 人 + AI 项目，没有 on-call、没有分页。承诺 SLA 就是承诺做不到的事 |
| 不是已验证的流程 | 每个标 `NOT_RUN` 的步骤都只是"设计好了"，不是"跑通了" |
| 不是销售话术 | §5 单独写"能说什么、不能说什么"，因为说错一句就是法律风险 |
| 不是 onboarding 文档 | 客户不需要读它。它是给我自己在客户面前不出错用的 |

**唯一一条硬规则**：任何一步，如果本文说"应该可以"，而实际不行，
**以实际为准，并回来改这份文件**。文档跟着事实走，不反过来。

## 1. 谁算"第一个客户"

| 算 | 不算 |
|---|---|
| 一个真实的人，用真实邮箱注册，且**自己决定**继续用 | 我自己建的账号（那叫测试账号，见 §6） |
| 走完注册 → 建工作区 → 至少一次真实使用 | 只点开首页就走（那是访客，不是客户） |
| 如果要收钱：付了**真钱**（哪怕 $1 可退） | 手工在数据库里给权限（那不是"客户付款"，是"我送"） |

`BIZ-04`（至少 1 个真实客户走通完整闭环）之所以是 BLOCKED，就是因为上表右列的事
一件都不能拿左列来顶。**用假单充客户，是这份文件最不该犯的错。**

## 2. 客户旅程：9 步，每步的完成判据与失败信号

时间轴按"一个客户从答应试用到付第一笔钱"排。左列是**我做什么**，右列是**怎么知道这步真的过了**。

### 步骤 0 · 在开口之前（前置，5 分钟）

| 动作 | 完成判据 | 当前状态 |
|---|---|---|
| 决定退款窗口是 7 天还是 14 天 | 两处文案一致（`/refunds` 与 `/pay.html`） | ❌ **未决**：14 天 vs 7 天同时在线（`08` §5.2） |
| 决定"客户付给谁" | 法律主体明确（谁开票、谁承担退款） | ❌ **未决**（`BIZ-03`） |
| 确认邮件通道在生产可用 | 能收到一封真实验证码 | ❓ **UNKNOWN**（见 §3-A） |

> 这三项没定之前，**不要对客户说"可以退款"**。说了就是承诺一个还没有承诺人的承诺。

### 步骤 1 · 邀请（2 分钟）

- 发一条带 `https://app.lokfeel.com/` 的消息，说明这是**早期版本**、可能中断、数据可能被清。
- 完成判据：对方回了"好，我试试"。
- 失败信号：对方问"这是什么" —— 说明落地页没讲清楚（`06` 记过：首页仍是交友叙事）。

### 步骤 2 · 注册（客户 3 分钟，我待命）

- 客户：点 "Create account" → 填邮箱 → **等验证码邮件** → 输码。
- 完成判据：`emailVerified` 变 true，能进 `/workspace`。
- 失败信号：**收不到验证码**。这是第一个客户最可能卡住的地方，处置见 §3-A。
- 当前状态：❓ `NOT_RUN`。注册接口会发验证码邮件（`/api/auth/register` → `/api/auth/verify`），
  但**生产是否配了邮件通道，从外部无法观测**（`/api/health` 没有 email 组件）。

### 步骤 3 · 首次登录（1 分钟）

- 完成判据：`/login` → 落到 `/workspace`，六个屏（Now/Studio/Field/Consent/Outcomes/Agents）都有内容或明确空态。
- 失败信号：白屏、或某屏显示"—"却不说为什么（那是 `UX-04` 的判据）。
- 当前状态：❓ `NOT_RUN`（我就是因为没有生产测试账号才没验过，见 §6）。

### 步骤 4 · 建第一个工作区（客户 5 分钟）

- 客户：一句话描述目标 → 点"编译工作区" → 拿到 `WorkspaceSpec` 画布。
- 完成判据：画布出现节点，且节点数据来自真实端点（不是手写拓扑）。
- 失败信号：转圈不出结果 → 查 `workflow-tick` 是否在跑（`05` §8 第 9 条：定时任务是否开启）。
- 当前状态：❓ `NOT_RUN`。**这是最可能"功能没在工作"的一步** —— outbox 的重试退避
  在没人触发 `scheduler.yml` 时根本不会推进。

### 步骤 5 · 给多少免费额度（我决定，30 秒）

- 当前没有"免费层"的产品定义（`10` 要做的事）。**不要临场承诺"永久免费"**。
- 安全说法：「早期版本，试用期内不收费；开始收费前会提前告诉你。」
- 完成判据：客户知道"什么时候会开始收钱"。

### 步骤 6 · 付费（客户 2 分钟，风险最高）

- 路径：`/pricing` → **307** → `/pay.html` → 点套餐 → 跳到 Gumroad 结账。
- 完成判据：Gumroad 侧显示金额与站内一致，付款成功，收到 Gumroad 收据。
- 失败信号（按可能性排）：
  1. **大陆网络打不开 Gumroad**（DNS 污染 + 12s 超时，已实测）⇒ 见 §3-B；
  2. 站内 `$12.99 / $99.99 / $32.99` 与 Gumroad 侧价格不一致（**未核**，无 Gumroad 账号）；
  3. 付完钱**回跳后会话已断**（`08` §5.3 第 3 条，**未验**）。
- 当前状态：❌ 不可执行。`payments.configured=false`（缺 4 个凭据），
  且付款页卖的是另一个产品（`08` §5.1）。

### 步骤 7 · 开通核对（我，5 分钟）

- 动作：确认订阅状态与该客户账号对应、权益生效。
- 完成判据：`/api/payments/status` 显示正确套餐；`isEntitled` 为真。
- 已知风险：**Creem 续费的入账逻辑本轮才修好**（原来完全不入账、幂等键撞键），
  但**没在真实网关上验过**（`PAY-02/PAY-10` BLOCKED）。首月正常不代表次月正常。
- 当前状态：❌ 不可执行（无凭据）。

### 步骤 8 · 首月服务（持续）

- 唯一承诺：**异步响应**，工作日 24h 内回。
- 不说"7×24"、不说"1 小时内"。说了就违约（§5）。
- 客户遇到问题时的分诊表见 `05` §7（8 类症状 Runbook）。

### 步骤 9 · 续费 / 取消 / 退款（客户随时）

- 取消：Gumroad 收据里自助取消（站内没有取消入口 —— 这是一个**真缺口**，见 §4-6）。
- 退款：按 §0 定下的窗口办；执行侧流程见 `04` §5。
- 完成判据：退款到账 + 订阅状态翻 `REFUNDED` + 客户收到确认信。
- 当前状态：❌ 退款链路只在协议层验过（`PAY-07` PASS，真实 SDK + 假服务端），
  **真实退款没做过**（`PAY-08` BLOCKED）。

## 3. 五个失败剧本

每条都写"客户会看到什么 / 我该做什么 / 怎么知道修好了"。没有步骤编号的空白，
说明**这一步还没有可执行的办法** —— 那比编一个办法更有用。

### A · 客户收不到验证码

| | |
|---|---|
| 客户看到 | "验证码已发送"，但邮箱没有（含垃圾箱） |
| 根因候选 | ① 生产没配邮件凭据（走沙箱捕获，看起来"发送成功"却没人收到）② 发件域 SPF/DKIM 未配 ⇒ 进垃圾箱 ③ Resend 额度用尽 |
| 处置 | ① 查 `/api/health` —— **没有 email 组件，查不到**；② 只能登 Netlify 看环境变量；③ 兜底：我用管理员权限手工置 `emailVerified`（**这属于"手工改数据"，必须记录在案**） |
| 怎么知道修好 | 让客户重试一次，能收到 |
| 状态 | ❌ **UNKNOWN**。这是本 playbook 最脆的一环：**注册的必经步骤没有可观测指标** |

> 这正是 `OPS-05`（业务指标不可观测）在客户面前的样子：不是"报表不好看"，
> 是"客户卡住了我不知道"。

### B · 大陆客户打不开付款页

| | |
|---|---|
| 客户看到 | 点了套餐，页面转圈 12 秒然后失败 |
| 根因 | Gumroad 在大陆 DNS 污染（已实测） |
| 处置 | ① 换通道（Creem/Stripe 大陆可用性**未验**）；② 或临时人工收款（**违反"不能造假单"吗？不违反 —— 但必须走真实收款渠道并如实记账**，不能手工改数据库冒充已付） |
| 状态 | ❌ 依赖 `BIZ-01` 的通道决策，未定 |

### C · 客户要求退款

| | |
|---|---|
| 客户看到 | 我先确认"在窗口内"，然后执行 |
| 前置 | **窗口必须先定**（7 或 14 天）。没定之前不要回答"可以退" |
| 处置 | `04` §5 六段 SOP：确认 → 原路退 → 翻账单状态 → 通知 → 记账 → 复盘 |
| 风险 | 退款要动 `invoice.payments[].payment.payment_intent`（`invoice.payment_intent` 自 dahlia 起已移除），这条链路只在假服务端验过 |
| 状态 | ❌ `PAY-08` BLOCKED |

### D · 客户要求删除数据

| | |
|---|---|
| 客户看到 | 我先给"影响面预览"，再问一次确认，然后才执行 |
| 处置 | `POST /api/v1/me/erasure`：默认 `apply=0` 只预览；只有 `apply=1` 才执行 |
| 已验 | 导出不执行、删除需显式 `apply=1`（`0/yes/true/裸 apply` 均不执行）—— 有 11 条单测 |
| 未验 | **真删一个客户的数据没做过**（需生产测试账号）；缓存与备份的物理限制见 `04` §6 |
| 话术 | 不说"彻底删除"。说"删除我们系统内的数据；备份会在 N 天内轮转掉"——N 必须真实 |

### E · 客户要发票 / 收据

| | |
|---|---|
| 现状 | 收据由 Gumroad 出（第三方）；站内**没有开票能力** |
| 处置 | 如实说"目前只有支付平台的收据，没有正式发票" |
| 风险 | 如果客户是企业，这一条可能直接让交易黄掉 —— 而**法律主体未定** ⇒ 现在也开不出发票 |
| 状态 | ❌ 依赖 `BIZ-03` |

## 4. 六个已知地雷（都是本轮实测出来的，不是猜的）

| # | 地雷 | 客户会怎么撞上 | 现在能不能绕 |
|---|---|---|---|
| 1 | 首访白屏 6.3 秒 | 手机上点开链接，等 6 秒才看到字（`08`） | 不能。TTFB 1.4s 是平台底座 |
| 2 | 付款页卖的是别的产品 | 点"定价"看到 "Hlua Pass"、"streaming"、"H-Points" | 不能。要改页面 |
| 3 | 退款窗口 7 天 vs 14 天 | 客户在两个页面看到不同承诺 | 能（改一处文案 = 10 分钟） |
| 4 | 大陆打不开 Gumroad | 点结账 → 超时 | 不能。要换通道 |
| 5 | 触控目标 16px 高 | 手机上点导航链接老点错（13/18 不达标） | 能（加 `min-height`，1 小时） |
| 6 | **站内没有"取消订阅"入口** | 客户想取消，找不到按钮，只能去 Gumroad 翻收据 | 不能。Gumroad 收据里有，但客户不知道 |

第 6 条是本节新发现的：`pay.html` 承诺 "cancel in one click"，
而那个 one click **在 Gumroad 的收据邮件里**，不在我们的产品里。
对客户来说，"我要取消"这件事的入口不在他正在用的产品里 —— 这是最容易变成投诉的一条。

## 5. 一页话术（能说 / 不能说）

| 能说 | 不能说 | 为什么 |
|---|---|---|
| "这是早期版本，可能中断" | "很稳定" | 冷启动 6.3s、无 on-call |
| "工作日 24 小时内回复" | "7×24 支持" / "1 小时响应" | 1 人项目，承诺即违约 |
| "退款按政策，14 天内可申请"（**前提：窗口已定**） | "随时可退" | 窗口未定时任何承诺都是空头 |
| "数据删除会告诉你影响哪些内容" | "彻底删除，一点不剩" | 备份与第三方副本有物理限制（`04` §6） |
| "我们用的是第三方支付平台" | "我们不接触你的卡号"（技术上对，但别引申成"我们很安全"） | 别把"没碰"说成"没问题" |
| "现在没有正式发票" | "可以开票" | 法律主体未定 |
| "你的数据不会被用来训练模型" | "你的数据绝对不会离开你的账号" | 有 10 家第三方处理者（`04` §7） |

## 7. 第一个客户当天的时间线（90 分钟）

给"客户就在线、我在旁边"的场景用。**这是唯一一种能在没有监控的情况下兜住的方式**。

| 时间 | 我 | 客户 |
|---|---|---|
| T-10min | 打开 `/api/health` 看一眼 `status`；确认 `payments.configured` 的真值 | — |
| T-0 | 发链接 + 一句"早期版本，有问题随时说" | 点开（等 3–6s） |
| T+3min | 待命，盯邮箱 | 注册，等验证码 |
| T+6min | 若没收到 → §3-A | 重试或换邮箱 |
| T+10min | 确认客户进了 `/workspace`（问他"看到几个屏"） | 登录 |
| T+15min | 待命，准备回答"这个按钮是干嘛的" | 建第一个工作区 |
| T+30min | 记录：哪一步卡了、卡了多久（这就是第一份真实 UX 数据） | 继续用 |
| T+60min | 问一句"如果没有我，你还会继续用吗" | 回答 |
| T+90min | 收尾：把今天卡住的点写回 `08`/`09` | — |

> 最后那问句是整份 playbook 里最重要的一句话。**它不是满意度调查，是留存测试**：
> 如果答案是"不会"，那么真正的结论是"产品还不该卖给第二个人"。

## 8. 这份文档的维护规则

1. 每跑一次真实客户，把 §6 的 `NOT_RUN` 改成 `RUN_AT <日期> <结果>`，**失败也写**。
2. 客户撞到的新坑，先加到 §4，再谈修复 —— 顺序反过来就会漏。
3. §5 话术表只做加法不做删减：说错过的句子留着，标"曾经说错"，比删掉有用。
4. 任何一步在实跑中与本文不符，**改本文**，不要改事实。

> 一句话：这份 playbook 现在的价值不在"它能指导什么"，而在
> **它把 15 项"没做过"逐条摆出来了**。0 客户的项目最危险的不是流程不熟，
> 是误以为流程已经跑通。
