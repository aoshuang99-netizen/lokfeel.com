## 1. 数据主体权利地图：我们**实际**能做到什么

这一节只写代码里真实存在的东西。做不到的不列进去，也不写"已规划"。

| 权利 | 入口 | 方法 | 鉴权 | 覆盖范围 | **不覆盖** |
|---|---|---|---|---|---|
| 访问 / 导出 | `/api/v1/me/export` | `GET` | 仅需登录 | `User`（脱敏）+ `Profile`（剔内部字段）+ 意图/参与/桥接/AgentRun/通知 | IM 会话与消息、匹配史（B2C legacy 域） |
| 删除 / 匿化 | `/api/v1/me/erasure` | `GET` 只读计划 / `POST ?apply=1` 执行 | 仅需登录 | 见 §3 动作清单 | 同上 |
| 撤回同意 | `/api/im/consent` | `DELETE` | 仅需登录 | `ConsentGrant` 置 `isRevoked` + 会话 `cachedConsentState` 归零 | — |
| 更正 | 无独立接口 | — | — | 走 `/dashboard/settings` 自助修改 | 无审计留痕（更正不需要，但删除需要） |

**关键结构约束**：导出与删除的对象**只有**会话这一个来源。

`/api/v1/me/export` 的 handler 签名是 `GET()` —— **一个参数都不接**。这不是"读了参数但没用"，而是根本没有读的入口。这一点被写成了断言（`expect(exportRoute.GET.length).toBe(0)`），因为"没有参数"和"有参数但忘了校验"在代码评审里长得一模一样。

## 2. 导出：能力边界与实操

### 2.1 已落地的脱敏

| 层 | 剔除内容 | 理由 |
|---|---|---|
| `User` | `password` / `tokenVersion` / `botConfig` | 导出物会落到用户手里（还可能被转发）。凭据哈希外流 = 离线爆破成本归零 |
| `Profile` | `adminNotes` | 内部运营备注，不是用户数据 |

版本号 `ACCOUNT_EXPORT_VERSION = '2026-10-16'` 写进导出文件，回答"这份导出按哪版清单生成"。

### 2.2 诚实的截断

单表上限 `EXPORT_ROW_LIMIT = 1000`。超出**只给计数 + `truncated: true`**，不静默截断成"看起来完整"。静默截断会让用户以为拿全了，实际少了 —— 这在个保法的"可携带"语境下比不导出更糟。

### 2.3 SOP：导出（六段）

| 段 | 动作 | 负责人 | 时限 |
|---|---|---|---|
| 1 受理 | 用户邮件至 `privacy@lokfeel.com`（或站内自助） | 运营（当前 = 创始人本人） | 收到即计时 |
| 2 核身 | 必须**从注册邮箱**发信，或已完成登录态自助导出 | 同上 | 1 个工作日 |
| 3 执行 | 用户自助：`GET /api/v1/me/export`；代客：**不允许** | — | 即时 |
| 4 交付 | 自助返回 JSON；邮件场合提供一个 7 天有效的下载链接 | 同上 | 3 个工作日 |
| 5 留痕 | 记录「谁、何时、通过哪条路径、导出了哪个 userId」到 `AuditLog` | 同上 | 即时 |
| 6 复核 | 确认导出物**不含** `password` / `tokenVersion` 字段 | 同上 | 交付前 |

**为什么不允许代客导出**：任何"管理员帮用户导出"的路径，都是一条"内部人批量拉走全站数据"的路径，且事后无法与合法导出区分。用户自己登录点一次的成本极低，没有代客的必要。

**时限依据**：个保法第 45 条要求"及时提供"，GDPR Art.15 要求 1 个月内。内部 SOP 收紧到 **3 个工作日**（刻意小于法定上限，给核身与异常留余量）。

## 3. 删除：两段式与不可逆边界

### 3.1 两段式闸门

```
GET  /api/v1/me/erasure          → 只读计划（可任意次调用）
POST /api/v1/me/erasure          → 同 GET，返回计划，不写任何东西
POST /api/v1/me/erasure?apply=1  → 真执行（不可逆）
```

只认字面量 `1`。`apply=0` / `apply=yes` / `apply` / `apply=true` 一律**不**执行 —— 这条被单测穷举钉住（`tests/lifecycle/privacy-rights-api.test.ts`「副作用闸门」组）。

### 3.2 为什么是"匿化 + 状态收窄"，不是裸删

三个理由，每条都是这台机器上的真实约束：

1. **`User.deletedAt` 全仓无业务查询在读**。只置 `deletedAt` 等于没删 —— 用户照样出现在发现页。所以必须让数据**本身**不可识别。
2. **`Profile.profileStatus` 才是各查询面的实际闸门**（发现/匹配/候选都以 `APPROVED` 为条件）。改成 `DEACTIVATED` + `isApproved=false`，匿化后的账号**自动**从所有用户面消失，无需改任何查询。
3. **裸删会打断别人的数据**：`ConnectionProposal` / `Outcome` 的另一侧是**对方**的记录；`AuditLog` / `TenantAuditEvent` 是合规证据。删 `User` 行会在对方面前留下悬空引用，并抹掉审计。

这也是 GDPR 里 "erasure + 最小留存" 的常见落法：保留**不可识别的最小骨架**（行在、id 在、PII 已清）。

### 3.3 执行顺序不是随意的

`executeErasure()` 的顺序是：**先关闸门，再清正文，最后清缓存**。

- 先关 `Profile.profileStatus`：即使后续某步失败，用户**已经**从用户面消失。失败方向落在"更不可见"一侧。
- 缓存放最后：前面任何一步抛错，都不该留下"缓存已清、库里却还有 PII"的组合 —— 那时缓存是唯一还带着 PII 的地方，却看起来已经处理过。

### 3.4 🔴 本次修掉的一处真实不一致

动作清单 `ERASURE_ACTIONS` 自述是「**单一真相源**：文档、接口报告、测试都引用它 —— 于是"删了什么/留了什么"不存在两份说法」。但它当时写的是：

```
SocialIntent · status → CANCELLED
```

而 `enum IntentStatus` 只有 **`ACTIVE | WITHDRAWN`** —— **没有 `CANCELLED`**。`erasure.ts` 实际写的是 `WITHDRAWN`。也就是说：

- 这份"真相源"和实现是**两份说法**；
- 清单里那个值**在枚举里不存在**，照它写代码会直接触发 Prisma 校验错误。

修法（已提交）：引入 `ERASED_STATUS` 常量，代码与文案共用同一个字面量；并加了漂移守卫 —— 断言清单点名的是 `WITHDRAWN`、不含 `CANCELLED`，且 `erasure.ts` 里不再出现硬编码的 `status: 'WITHDRAWN'`（含反向对照，先证明这条检测真能抓到硬编码）。

### 3.5 覆盖边界（诚实清单）

✅ **已覆盖**：账号凭据、档案全部可描述属性（含 age/gender/sexuality 等粗粒度画像 · 非空列用中性哨兵而非留原值）、意图正文、参与状态、桥接 opt-in、Agent 原始文本、站内信、用户维度缓存。

⚠️ **保留**：`Membership`（组织审计）、`ConnectionProposal`/`ProposalDecision`/`Outcome`（对方侧与合规证据）、`AuditLog`/`TenantAuditEvent`（合规证据，本身不承载 PII）。

❌ **未覆盖**：IM 会话与消息、匹配史（属 B2C legacy 域）。

> **因此不得对外宣称"删除账号会删除您的全部数据"。** 正确说法见 §8 的对外话术。

### 3.6 「删了库」≠「删干净了」

`who-liked-me` 缓存的值里含**别人的**档案快照（displayName/avatar/age/city/gender/relationshipGoal）。库内匿化完成而缓存未失效，该用户会在**他人的**"谁喜欢过我"列表里继续以原昵称出现，最长 90 秒（TTL 60s + jitter 30s），**且没有任何报错**。

所以缓存失效是执行的**组成部分**：本人键按精确键失效；`who-liked-me:` 前缀**全局**失效（它的键属于他人、值里含本人快照，按 id 找不到）。执行结果把 `cache.keys` / `cache.prefixes` 显式回给调用方 —— "清了"与"忘了清"在响应里必须长得不一样。

## 4. 删除 SOP（六段）

| 段 | 动作 | 判据 | 时限 |
|---|---|---|---|
| 1 受理 | 用户在设置页自助发起，或邮件至 `privacy@lokfeel.com` | 必须来自账号本人 | 即时计时 |
| 2 核身 | 登录态即核身；邮件场合必须以**注册邮箱**发信 | 核身不通过**不得**执行 | 1 个工作日 |
| 3 计划 | 调 `GET /api/v1/me/erasure`，把 `impact` 逐项读给用户 | 至少要看到「保留项」与行数 | 同一次会话 |
| 4 确认 | 明确告知**不可逆**（原邮箱/昵称回不来）、保留项有哪些 | 用户书面确认 | 同一次会话 |
| 5 执行 | `POST /api/v1/me/erasure?apply=1` | 只走这一条路径 | 3 个工作日 |
| 6 留痕 + 复核 | 保存 `plan`/`applied`/`cache` 三份 JSON；核对 `applied` 与 `plan.impact` 是否一致 | 不一致 = 期间有新写入，需说明 | 即时 |

**对账口径**：`applied` 是执行时的 `plan.impact`，不是执行后重新统计。两者语义不同 —— 前者是"计划时的快照"，后者会被并发写入污染。若执行前后行数差值与计划不符，必须在报告里注明"期间有新增数据"，**不能**悄悄改数字。

**单人公司下的职责分离**：只有一个人，做不出真正的双人复核。补偿手段是**把复核变成机器可读的**：`plan` 与 `applied` 都是结构化 JSON，且 §3.5 的边界写死在常量里。人可能记错，常量不会。

## 5. 退款 SOP

### 5.1 🔴 先解决一个冲突：对外承诺有两个版本

| 面 | 文案 | 出处 |
|---|---|---|
| 站点退款页 | **14 天**冷静期（首购、未大量使用高级功能） | `src/app/(public)/refunds/page.tsx` §2（Last updated: May 21, 2026） |
| 实际下单页（Gumroad 店面） | **7 天**，对最新一期账单 | `public/pay.html:167` |

客户实际付款时看到的是 **7 天**；站点说 **14 天**。两个数字同时在线，客户可以挑对他有利的那个，而我们没有一条能站住的口径。

**本期采用的仲裁规则（立即生效，直到文案统一）**：

> **以对客户更有利者为准** —— 即 **14 天**。

理由：7 天是我们自己写的、可以改；14 天是已经公示的承诺，单方面收紧属于对已公示条款的不利变更。宁可多退，不可少退。这条规则写进 SOP，而不是"等想清楚了再说"，因为"没想清楚"期间正好会有真实退款请求进来。

**这是 BLOCKED 的法律部分**：14 天是否来自欧盟/英国消费者撤回权（数字服务需客户明示同意方可提前开始履行）、以及面向中国大陆用户时"7 天无理由"是否适用数字订阅，**需要法律意见**，不是工程能定的。已列入 §9 决策项。

### 5.2 退款六段

| 段 | 动作 | 判据 | 时限 |
|---|---|---|---|
| 1 受理 | `billing@lokfeel.com` 收信，登记工单（账号邮箱、交易号、原因） | 缺交易号也要受理，由运营反查 | 收到即计时 |
| 2 核身 | 核对发信邮箱 = 订阅账号邮箱；异常时要求提供交易号后四位 | 核身不通过不得退 | 1 个工作日 |
| 3 判定 | 对照 §5.3 判据表 | 判据外的情形 → 上报，不自行拒 | 5–7 个工作日（沿用已公示文案） |
| 4 执行 | Stripe 通道：`POST /api/admin/subscriptions/[id]/refund`（能力 `payment.refund`，`dangerous: true` 自带审计）；Gumroad 通道：Gumroad 后台手动退 | 必须走这两条，不得私下转账 | 批准后即时 |
| 5 对账 | ① 网关回执（Stripe refund id / Gumroad refund）② `Payment.status = REFUNDED` ③ 金额与币种与账单一致 | 三者缺一即视为未完成 | 1 个工作日 |
| 6 归档 | 工单写结论、金额、凭据 id；订阅状态按规则收窄 | — | 即时 |

### 5.3 判据表

| 情形 | 判 | 说明 |
|---|---|---|
| 技术故障导致付了钱用不了 | 退 | 全额 |
| 重复扣款 | 退 | 重复的那笔全额 |
| 未授权扣款 | 调查后退 | 需先核身；疑似盗卡同时上报 |

| 首购冷静期 | 退 | **窗口见 §5.1（当前 14 天）** |
| 已消耗的额度 / 已用高级功能 | 不退 | — |
| 纯粹改主意且已用高级功能 | 不退 | — |
| 因违规被封号 | 不退 | — |

### 5.4 代码现状（诚实）

- 退款逻辑集中在 `src/lib/stripe/refund.ts`，两条 admin 路由共用 `createSubscriptionRefundHandler()`。历史上两份复制实现都在 `invoice.payment_intent` 上恒 400（该字段自 Stripe `dahlia` 起已移除）—— 已修，且 CI 常态跑 `scripts/qa/refund-e2e.mjs`（真实 SDK + 本地假 Stripe 服务端，5 场景 19 断言 + 变异）。
- 但**真实扣款一次都没跑过**：`payments.configured=false`，4 个凭据（`STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` / `CREEM_API_KEY` / `CREEM_WEBHOOK_SECRET`）未填。协议层绿 ≠ 能退款。
- Gumroad 通道**没有 API 自动化**：Gumroad 在大陆不可达（DNS 污染 + 12s 超时），退款只能在能访问 Gumroad 的环境手动操作。这是当前架构的一个已知不对称。

## 6. 第三方处理者清单（数据出边）

删除请求**不会**同步删除第三方侧的数据。这是最常见、也最容易被误解的一条，必须逐家写清。

| 处理者 | 处理什么 | 删除时是否同步 | 缺口 |
|---|---|---|---|
| Turso（libSQL） | 主库全量 | ✅ 是（就是主库） | 快照 / PITR 窗口内的旧副本仍含原值，见 §7 |
| Upstash Redis | 会话、`who-liked-me` 等缓存 | ✅ 是（前缀全局失效） | 最长 90s 窗口，见 §3.6 |
| Stripe | 客户 id、订阅、发票、退款 | ❌ **否** | 金融记录受当地法留存义务约束，**不应**删；但需在隐私政策明示"支付记录依法保留" |
| Creem | checkout、订阅、交易 | ❌ **否** | 同上 |
| Gumroad | 店面订单、订阅、退款 | ❌ **否** | 同上；且退款为手动 |
| Resend（邮件） | 收件地址、投递事件 | ❌ **否** | 需在后台手动删除联系人，或依赖其保留策略 |
| Sentry | 错误事件（`NEXT_PUBLIC_SENTRY_DSN` 配置后生效） | ❌ **否** | 🔴 **无 `beforeSend` 脱敏** —— 错误消息里若出现邮箱/正文，会被发出去。已列行动项 |
| Firebase / firebase-admin | 推送/鉴权 | ❌ **否** | 需确认实际启用的能力范围 |
| Cloudflare / Netlify | 请求日志、边缘缓存 | ❌ **否** | 按各自保留期（通常 30 天内）自然过期 |
| WorkBuddy 云端 LLM | 提示词与补全（Living Workspace 生成时） | ❌ **否** | 生成内容属用户数据，需在 DPA 层确认不用于训练 |
| Google / Twitter OAuth | 登录身份 | ❌ **否** | 授权可在对方后台撤销 |

**因此对外话术必须区分三档**（见 §8）：我们控制的库里删了 / 我们这边第三方要另行处理 / 金融记录依法留存。

## 7. 日志与备份：删除的物理限制

| 载体 | 删除是否生效 | 真实行为 |
|---|---|---|
| 主库行 | ✅ 即时 | 匿化 + 状态收窄 |
| Redis 缓存 | ✅ ~即时 | 精确键 + 前缀全局 |
| `AuditLog` / `TenantAuditEvent` | ❌ 保留 | 合规证据，不承载 PII（actor 是软引用） |
| 数据库备份 / 快照 | ⚠️ **延迟** | 备份轮转周期内，旧快照仍含原值 |
| Sentry 事件 | ❌ 否 | 按 Sentry 保留期 |
| Netlify / Cloudflare 日志 | ⚠️ 自然过期 | 通常 30 天内 |

**必须写进隐私政策的句子**：

> 删除请求在 3 个工作日内于生产库生效。备份中的副本会在备份轮转周期结束后自然消失，我们不为此单独改写历史备份。

这句话现在是**空的** —— 因为备份轮转周期没定。Turso 免费计划的实际保留窗口需确认后填上具体数字，在此之前不要对外承诺"立即永久删除"。

## 8. 对外话术（可直接用的三档）

**档 1（最保守，推荐默认）**

> 您可以随时在「设置 → 隐私」导出自己的数据，或申请删除账号。删除后，您在 LokFeel 上的档案、意向、站内信与授权会在 3 个工作日内清除或匿化，账号无法再登录、也不会再出现在任何人的列表里。支付记录依当地法律要求保留，不含您的档案内容。

**档 2（补充第三方）**

> 若您通过 Gumroad / Stripe 付款，相关交易记录由这些支付服务商按其自身政策保留，需另行联系他们处理。

**档 3（禁止使用）**

> ~~删除账号会彻底删除您的全部数据，不可恢复。~~

—— 假的。未覆盖 IM 消息与匹配史，备份与第三方也不受控。

## 9. 演练与证据

### 9.1 已完成的演练（可在 CI 复跑）

`tests/lifecycle/privacy-rights-api.test.ts`（11 例）——路由级契约：

| 组 | 断言 | 守的是什么 |
|---|---|---|
| 身份关卡 | 匿名 → 401，且导出/计划/执行**一次都没被调用** | 未通过身份就不该产生任何数据操作 |
| 越权 | `GET.length === 0`；`?userId=受害者` 仍只作用于本人（导出与删除各一条） | 对象只能来自会话 |
| 副作用闸门 | `GET` 不执行；`POST` 无 `apply` 不执行；`apply=0/yes/true/裸 apply` 都不执行；`apply=1` 才执行 | 手滑一次不该毁掉账号 |
| 可断言性 | 执行后返回 `cache.prefixes` 非空 | "清了缓存"与"忘了清"必须长得不一样 |
| 错误映射 | `NotFoundError` → 404，不是 500 | 领域结论不退化 |

配套的语义层测试（已存在）：`tests/lifecycle/account.test.ts`（政策 + 本次新增的枚举漂移守卫）、`tests/lifecycle/policy.test.ts`（保留期判定）。

### 9.2 未能完成的演练（BLOCKED，原因写在明面上）

**不接受替代品**：用 mock 造出来的"导出成功"不能算这项证据 —— V17 硬约束里写了"不能把 Mock 当客户数据"。所以这里记 BLOCKED，不记 PASS。

### 9.3 解除 BLOCKED 的最短路径

1. 用一次性邮箱在生产注册一个测试账号（跳过 OAuth，走邮箱密码）；
2. 造 3 条最小数据：一条 `Profile`、一条 `SocialIntent`、一条 `Notification`；
3. `GET /api/v1/me/export` → 存 JSON → 断言 `password`/`tokenVersion` 不存在、行数与 §9.1 一致；
4. `POST /api/v1/me/erasure`（不带 apply）→ 存计划；
5. `POST /api/v1/me/erasure?apply=1` → 存结果；
6. 用只读 SQL 逐表计数：`User` 行在但 `email` 匹配 `erased+`、`Profile.profileStatus=DEACTIVATED`、`SocialIntent.status=WITHDRAWN`、`Notification` 计数为 0；
7. 全部产物落 `docs/implementation/v17/test-results/`，文件名带时间戳。

第 1 步会向生产库写入一个账号 —— 属"客户隐私数据"边界之外（是我们自己的测试账号），但与删除动作一样不可逆，**执行前需要一次明确确认**。
