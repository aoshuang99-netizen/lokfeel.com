# T05 · risks — 风险与残留

> 分级：🔴 上线阻断 / 🟡 需关注 / 🟢 已消解（保留记录以免后人重复踩）。
> 每条都写"**为什么**它是风险"与"**什么时候**必须消解"，而不是只贴标签。

---

## 🔴 R1 — 介绍执行点是**同步**的：AC-06 证的是并发安全，不是投递可靠性

**状态**：本刀实现了 `introduceConnection()` 这一个**同步执行点**，并把全部分量压在
"执行的那一刻再校验 + CAS 写入"上。**没有** outbox、没有重试、没有超时、没有死信、
没有人工接管。

**具体表现**：AC-06 的原文是"**延迟任务**发送前再次校验授权和过期状态" ——
它假设介绍是一个**被延迟投递的任务**。本刀用一个同步端点证明了"校验发生在执行那一刻"
（这正是 race condition 的要害），但没有证明"任务会可靠地被投递"。
如果介绍将来改由队列驱动，**校验代码必须原样搬过去**，而不是"因为在队列里所以安全了"。

**为什么标 🔴**：这是**与卡片定义的差额**，不是遗漏。卡片的完整范围
（队列/Temporal、outbox、重试、超时、死信、人工接管、邮件沙箱）明确属于 **T06**。
把它标成"AC-06 已完整实现"会是过度声明。

**消解时机与方式**：**T06**。届时要点：
- 把 `evaluateIntroducibility()` + `loadLiveParties()` 两段**原样**放进投递前的最后一个钩子；
- 队列任务的幂等键用 `(proposalId, 'introduce')`**固定**，使重投递不会产生第二条介绍
  （今天的端点是 `updateMany({introducedAt: null})` 的 CAS，天然只成功一次 —— 换成队列后
  这条性质必须显式重建）；
- 引入队列后会多出一个今天不存在的失败模式：**校验通过但投递失败**。需要
  "已介绍但通知未发出"的可观测态（本刀没有）。

## 🔴 R2 — 隔离仍是应用级，不是数据库级（继承 T01–T04）

**状态**：libSQL 没有 RLS。提案服务的隔离完全靠 `proposals.ts` 里的写法：
所有查询带 `organizationId`。

**T05 的具体表现**：本刀新增了两条**"我"必须恰好是当事人之一**的读路径
（`listMyProposals` / `listIntroductions`）。谓词写成
`OR: [{ proposerId: userId }, { candidateId: userId }]` 并且**不接受调用方传参**
（写死在服务层）。这里出错的影响面比 T04 更隐蔽：漏掉谓词不是"看到别人的候选"，
而是**直接看到别人的提案全文（含 rationale 与双方表态）**。

**已做的补偿**：
- 服务层入口只接受 `TenantContext`；
- `decideProposal` 对非当事人回 **403**，对跨租户回 **404** —— 两者刻意区分：
  "存在但不关你的事"与"不存在"是两种答复，混成一个会让跨租户探测变得可行；
- 分享令牌入口**二次校验 membership**（`resolveShareTokenTenant`）；
- 单测有"旁观者 → 403"与"跨租户 → 404"两条用例。

**残余**：编译期无法强制。彻底消除要靠 M6（PostgreSQL + RLS）。

## 🟡 R3 — 供给侧单点：`proposal.create` 是 OPERATOR+，没有它没人能发起提案

**状态**：权限设计是刻意的（牵线由社群主理人发起）。但它有一个**运营后果**：
一个社群若没有任何 OPERATOR，**提案流程整体不可用** —— 而界面上不会解释原因
（普通成员在候选页只看到"去我的连接看提案"，而那里永远为空）。

**为什么标 🟡 而不是 🔴**：这是产品规则而非缺陷。但"**空的原因不可见**"是缺陷 ——
与 T04 花力气做"无候选时必须说出口原因"是同一个原则，本刀**没有**做到等价的一件事。

**消解时机与方式**：T07（SaaS Console）应有"组织角色/成员管理"，
并能显示"本社群当前有 N 名运营"。在此之前，缓解手段是运营手册层面：
新社群开通时确保至少一名 OPERATOR。

## 🟡 R4 — 提案创建后**对方不会被通知**

**状态**：没有邮件、没有站内信、没有推送。提案创建成功只体现在
`/m/<token>/proposals` 这个页面上 —— 需要**被介绍方主动打开**才会看到。

**具体表现**：真实场景里被介绍方根本不知道有东西在等他。AC-04 的语义
（"双方各自同意"）在技术上成立，但**流程上会卡住**：一个没人通知的同意请求，
转化率近似为零。

**为什么标 🟡**：这是产品完整性问题，不是安全性问题；且卡片的 T05 范围里
并没有"通知"。但不写下来，读者会误以为"双边同意已经可以上线用了"。

**消解时机与方式**：**T06**（它的范围明确包含"邮件沙箱"与可靠投递）。
届时的要点：通知内容**不得**包含 rationale 全文与对侧档案 ——
它是"你有提案待处理"的提示，不是一次披露（否则通知渠道会绕开 `discloseSubject()`）。

## 🟡 R5 — `EXPIRED` 是派生值：`?states=` 过滤发生在装配之后

**状态**：库里没有 `EXPIRED`，它由 `expiresAt` 现算。因此
`GET /proposals?states=EXPIRED` 的过滤只能在装配完成后做（已在路由注释里写明）。

**风险的具体形状**：这不是"性能问题"，而是**"优化即失效"**：
日后有人把它下推进 SQL 时，`EXPIRED` 会**静默**变成"过滤不掉"
（因为 SQL 里根本没有这个值可匹配），而不是报错。

**已做的补偿**：`ALLOWED_STATES` 常量 + 路由注释 + 单测覆盖
"按 EXPIRED 过滤"的用例（若哪天有人改了实现，这条用例会红）。

**消解时机**：M6 迁 PG 时可以引入生成列（generated column）把派生值落库，
届时才真正能在 SQL 层过滤。在那之前**不要**为了"省一次内存过滤"而下推。

## 🟡 R6 — 撤回**改变不了已经发生的事实**

**状态**：撤销只在 `introducedAt === null` 时能阻止介绍。一旦介绍已落地，
`decideProposal` 对任何表态一律 `409`（含 `REVOKE`）—— 这是**刻意**的：
介绍是已完成的事实，允许"撤销"会给用户"信息被收回"的错误预期
（对方早已看到档案、早已收到联系方式）。

**残余风险**：用户想"停止联系"时，唯一的正确出口是 **Block**，
而 Block 不属本任务范围。若 T05 上线而 Block 尚未可用，会出现一个
"用户想撤但撤不掉"的窗口 —— 界面上必须说清（已建立的卡片**不提供任何动作**，
因此用户不会误以为点了撤回就能收回）。

**消解时机**：Block/举报属既有 B2C 能力，需要一次**入口可达性**的核对
（确认从"已建立连接"卡片能走到 Block）。建议挂在 T07 或 T12。

## 🟡 R7 — `ProposalDecision` 是**当前表态**，不是表态流水

**状态**：`PRIMARY KEY(proposalId, personId)` —— 每人每提案至多一行。
先 accept 后 revoke 时，本行被**覆盖**。

**残余风险**：库里查不到"这个人曾经同意过、后来改主意了"。
不可抵赖的追加式记录只在 `TenantAuditEvent` 里（`proposal.accepted` / `rejected` /
`revoked`，含 `{role, from, to}`），而**审计写入是 `.catch(() => {})`** ——
即"审计失败不影响业务"。

**为什么这样定**：这与 T02/T03 的取向一致（业务可用性优先于审计完整性），
但如果将来有合规要求"每一次表态都必须留痕且可举证"，这两点都要改：
① 决策表改成追加式（或双写）；② 审计写入改为**事务内**、失败即回滚。

**消解时机**：合规评审时（AC-10 数据生命周期批次）。

---

## 🟡 R8 — 提案列表无分页

**状态**：`limit` 默认 50，没有游标、没有总数。

**具体表现**：一个活跃社群的运营可能在一个任务下发起上百条提案，
而被介绍方（成员）会看到全部与自己相关的。50 条截断**静默**发生 ——
用户不知道"还有更多"。

**消解时机**：T12（负载与规模验证）。在此之前，界面层面应至少提示"仅显示最近 N 条"
（本刀未做）。

## 🟢 R9 — 同意过之后的动作清单冗余（本刀修掉）

`availableActions()` 是**角色无关**的纯函数，所以"我已同意"这层过滤在装配处。
**修复前**只滤掉 `ACCEPT`，于是"我已经同意过"的提案上同时出现「拒绝」与「撤回」——
两者产生**不同**的 `ProposalDecision`（REJECT vs REVOKE）却导致**相同**终态，
审计里"曾经同意过"被覆盖成"拒绝"。

**修复**：同意过之后只保留 `REVOKE`（撤回同意才是改主意的准确语义）。
回归证据：`proposals-api.test.ts` 断言 `actions === ['REVOKE']`；
E2E 在「双方已同意」的卡片上断言 `proposal-action-accept` 与
`proposal-action-reject` 的 `toHaveCount(0)`。

## 🟢 R10 — 契约路径多一段（本刀修掉，值得留记录）

`{connectionId}` 在 T05 的三个端点上**就是提案 id**，路径只有 3 段。
实现期犯过 3 次同一个错（写成 `/connections/proposals/{id}/consent` 这种 4 段），
**每一次都通过了单元测试** —— 因为单测直接 `import` handler 并手工传 `params`，
根本不经过路由匹配。只有真正跑 E2E 的浏览器点击与 `ctx.request` 才得到 404。

**教训**：**路径形状属于路由层，只有端到端能证。**
凡是"手工传 params"的测试，都覆盖不到它。

## 🟢 R11 — E2E 断言"成功提示文案"是竞态（本刀修掉）

第一版 E2E 对终态动作（拒绝 / 撤回）断言"点击后出现「已关闭」提示"，
间歇性失败。根因不是功能坏了：服务端其实已 `200`、库里 `status` 已是 `REJECTED`，
**但**终态动作成功后 `router.refresh()` 会让闭合的卡片**不再渲染动作区**
（`page.tsx` 里 `actions.length > 0` 才渲染 `ProposalActions`），
那条提示**随刷新被卸载** —— 断言它等于在抢一个瞬态 DOM。

**修复**：断言**刷新之后依然成立**的事实（卡片移入「已结束」、状态为终态、
无任何动作），并以"等 POST 响应"代替"等 DOM 提示"。
详见 `tests.md` §7.3。

> 这条值得单独记：**"用户能看到的"和"刷新后仍然成立的"不是同一类事实。**
> 断言前者的用例，在 dev 下必然偶发；后者才是可以长期守住的判据。
