## D-09｜历史提交里的凭据是否仍有效

**当前事实**（本轮实测，非引用旧结论）

1. 与生产**逐一哈希比对**（只输出是否相同，不输出值）：

| 键 | `.env.test` 里有 | 生产里有 | 值相同？ |
|---|---|---|---|
| `AUTH_SECRET` | 是 | 是 | **不同** |
| `DATABASE_URL` | 是 | 是 | **不同** |
| `RESEND_API_KEY` | 是 | 是 | **不同** |
| `PUSHER_SECRET` / `PUSHER_KEY` / `PUSHER_APP_ID` | 是 | 是 | **不同** |
| `AUTH_URL` | 是 | 是 | **不同** |

⇒ **这些值不能用来伪造生产会话、访问生产库或发信。**
2. 键值形态也支持"夹具"判断：`OPENAI_API_KEY` 仅 18 字符、`RESEND_API_KEY` 仅 11 字符（真实 key 远长于此）。
3. `.env.test` 仍被 `tests/setup.ts` 加载 ⇒ **删掉会打断 Jest**，不能简单删文件。
4. 既有审计（`docs/SECURITY-HARDENING-2026-09-29.md`、`REPO_AUDIT.md`）已记录"全为 test-* 占位"，与本次哈希比对一致。

**业务风险**：剩下的风险不是"生产被攻破"，而是
- 若 `OPENAI_API_KEY` / `LINKEDIN_CLIENT_SECRET` 在**别的地方**仍然有效（例如旧账号），那段历史就是公开可读的；
- 这一点**无法在不实际调用第三方的情况下验证** ⇒ 记为 `UNKNOWN`。

**选项**：① 轮换那两个"可能别处仍有效"的键 + 保留 `.env.test` 作为夹具 ② 改写 git 历史（**不推荐**：会改写已发布提交）③ 什么都不做

**推荐：①**。轮换成本极低，且不需要动历史。

**需要你批准**：✅ 是（轮换会短暂影响使用该 key 的旧代码——如果还有的话）。

**验收标准**：两个 key 在各自平台被吊销/重建；`.env.test` 仍能跑通 Jest；CI `Secret scan` 保持绿。

## D-11｜是否给 `Subscription` 加 `provider` 列

**当前事实**
- `src/lib/creem.ts` 把 Creem 的订阅 id 写进 **`stripeSubscriptionId`**（注释写着 "reuse field"）⇒ 从库里分不出这笔订阅属于谁。
- 本轮用 `resolveCancelProvider()` 按"当前只配了一家凭据"推断；两家都配时**拒绝**自助取消（409 `PROVIDER_AMBIGUOUS`）。
- 加列要动生产 Turso（snapshot→plan→apply→verify），属不可逆迁移。

**业务风险**：两家同时配置时，取消订阅必须人工介入；这与"自助取消"的产品承诺不一致。

**选项**：① 批准并在发布窗口内迁移 ② 维持现状（两家都配就拒绝）③ 约定"同一时间只用一家"写进运维手册

**推荐：③（短期）+ ①（下一次需要迁移时一起做）**。当前不配支付，②/③ 的实际影响为零；
**不要为这件事单开一次生产迁移**。

**需要你批准**：✅ 是（涉及生产库结构）。

**验收标准**：`resolveCancelProvider()` 的行为与所选方案一致，且有测试把守；若选①，迁移后 `describeCancelEligibility()` 能区分 provider。
