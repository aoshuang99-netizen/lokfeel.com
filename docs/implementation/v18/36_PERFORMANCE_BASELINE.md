# 生产性能基线（WB18-36）

> 这一份的目的不是"打个分"，而是把"性能还有优化空间"换成**具体到哪个环节花了多少毫秒**。
> 采集脚本：`scripts/qa/perf-baseline.mjs`（只测不判，永远 exit 0）。
> 原始数据：`reports/perf/baseline-2026-10-23.json`（生成物，不入库）。

- 采集时间：2026-10-23 07:14Z
- 目标：生产 `https://app.lokfeel.com`（`dc102cd`）
- 样本：每路由 **5 次冷**（每次新 context，空缓存）+ **5 次暖**（同 context 连续导航）
- 条件：390×844 / DPR 2 / 移动端 UA / CPU **4× 降速** / 下行 1.6 Mbps / 上行 750 kbps / **+150ms RTT**

> ⚠️ **采集环境的诚实边界**：150ms 是**叠加在本机真实 RTT 之上**的，
> 本机到该站点并非机房直连。所以下面的绝对值偏悲观，
> 可用于**同机前后对照**与**路由之间比较**，**不可当作真实 4G 用户的场域数据（field data）**。
> 脚本里也写明了这一点，避免下一个人把它当官方分数。

## 3. 三个被数据推翻/修正的前提

### 3.1 "TTFB 占 LCP 42–68%" —— 不成立

实测首字节只占 LCP 的 **8%–20%**。差别来自**口径**：
`responseStart - requestStart`（首字节）与
`responseEnd - responseStart`（正文下载）是两件事，实测两者能差一个数量级
（首页 770ms vs 273ms；`/login` 247ms vs 265ms；极端情况见过首字节 824ms / 正文 929ms）。

把两者混成一个"TTFB"，就会得出"TTFB 是瓶颈"或"TTFB 不是瓶颈"两个相反的错误结论。
所以脚本里**分成两列记**（`navTtfb` / `docDownload`），报告里也分开写。

### 3.2 "LCP 慢 = 图片大" —— 在本站不成立

三个公开路由的 **FCP ≈ LCP**（首页 3784 = 3784；`/pay.html` 2348 = 2348），
说明 LCP 元素就是**首屏第一次绘制出来的那块内容**，而不是一张慢慢加载的图。
`/login` 有 380ms 的 FCP→LCP 差，但主体仍是首绘时间。

换句话说：LCP 被**首绘**决定，首绘被 **渲染阻塞资源 + 主线程**决定。
图片不是首要瓶颈 —— 这条与任务书里"禁止继续默认把图片作为首要瓶颈"的提醒一致，
现在有数据支持它。

### 3.3 "冷启动可以忽略" —— 不成立

| 路由 | 冷 LCP | 暖 LCP | 倍数 |
|---|---|---|---|
| `/` | 3784 | **1024** | **3.7×** |
| `/pay.html` | 2348 | **792** | **3.0×** |
| `/pricing` | 3044 | 1652 | 1.8× |
| `/login` | 3172 | **3172** | **1.0×** |

前三行说明"首次访问"和"再次访问"是两个世界；`/login` 是唯一**暖态毫无改善**的页面
（暖态首字节甚至测到 1847ms）—— 它的瓶颈根本不在网络。

另外 `/api/health` 首次调用读到 `dbLatency: 4770ms`，随后三次是 `138 / 10 / 6`ms：
**冷启动时第一次连远程 Turso 的成本约 4.8 秒**。发布后的第一波流量会踩到它。

## 4. 瓶颈排序（按证据强度，不按感觉）

### ① 首页的 JS 体积与主线程（`/`）

- 272KB / 14 个请求；TBT **1318ms**（4× CPU 下降速后）。
- 首页最重的一个 chunk 是 **123KB 单文件**（`/_next/static/chunks/0_pgcg9-j791z.js`），
  在 1.6 Mbps 下传输耗时约 3.3 秒 —— 它和另外 5 个 chunk **并行抢同一条 200KB/s 的带宽**。
- 冷 LCP 3784 → 暖 LCP 1024 的差值，基本就是"下载 + 解析这批 chunk"的成本。

### ② 登录页的 JS 体积与主线程（`/login`）

- **239KB / 13 个请求**，TBT **1153ms**。
- 一个"邮箱 + 密码 + 提交"的表单不需要 239KB 的运行时；
  且这一页**暖态 LCP 完全没有改善**，说明即使资源全在缓存里，主线程仍然要花 1 秒以上才画得出首屏。

### ③ 连接建立（pre-request 435–895ms）

`navigationStart → requestStart` 在首页中位 **770ms**，这段包含 DNS + TLS + 排队。
它和"首字节"是两段不同的时间，优化手段也不同（连接复用 / 预连接 / CDN 就近）。

### ④ 第三方脚本

`static.cloudflareinsights.com` 在四个路由上都出现，单次耗时 **923–3114ms**。
它是异步的，不直接阻塞首绘，但在 1.6 Mbps 的链路上**和首屏资源抢带宽**。
是否保留取决于是否在用 Cloudflare Web Analytics。

### ⑤ `/pricing` 的 307（发布后自然消失）

当前 `/pricing` 比 `/pay.html` 多花 **约 0.7 秒**（3044 vs 2348），主要就是那一跳重定向。
HEAD 已把 `/pricing` 改成真实页面 ⇒ **发布本身就会拿回这部分**。

## 5. 建议的下一步（按性价比排序，均未实施）

| # | 动作 | 预期效果 | 风险 |
|---|---|---|---|
| 1 | 发布 `1170073`（`/pricing` 不再 307） | `/pricing` 省约 0.7s | 低（已在 CI 验证） |
| 2 | 拆 `/login` 的 239KB 包（该页只有一个表单） | `/login` TBT 从 1153ms 显著下降；暖态才会开始有收益 | 中（要动组件边界，需回归登录链路） |
| 3 | 首页首屏 chunk 瘦身 / 延迟非首屏组件 | `/` 冷 LCP 的主要杠杆（272KB → 目标 <150KB） | 中（可能影响交互，需保 E2E） |
| 4 | 给函数加保活（cron 每 5 分钟打 `/api/health`） | 消掉首次访问的 4.8s DB 冷连接 | 低，但会增加调用次数（免费额度内需核算） |
| 5 | 评估移除 Cloudflare Insights beacon | 少一段带宽竞争 | 低（会失去一份分析数据） |

**不做的事**：不为了跑分去删功能、不改权限与业务逻辑、不在没有前后对照的情况下宣布"优化完成"。
