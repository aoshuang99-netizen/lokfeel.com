🏗️ 系统架构 架构设计
分层权限检查：前端路由守卫 → API 中间件 → 数据库查询层，三层联动。

🔑 权限检查流程

1
前端路由守卫
usePermission() Hook 检查 hasPermission(role, permission)
→
2
Next.js API Middleware
requirePermission() 验证 session + 角色 + 权限
→
3
Prisma 查询层
AdminUserRole → AdminRolePermission → AdminPermission
→
4
AdminRoleAudit 审计
所有变更写入审计日志，支持回溯

📊 数据库模型关系

A
User（复用）
原有 UserRole: USER / ADMIN / SUPER_ADMIN
B
AdminUserRole（N:1→User）
管理员-角色关联，含 department / expiresAt
C
AdminRole（7个预定义）
SUPER_ADMIN / ADMIN / MODERATOR / ANALYST / SUPPORT / CREATIVE / VIP_AGENT
D
AdminPermission（45+条）
code / name / category / isDangerous
E
AdminRolePermission（N:N）
角色-权限关联，grantedBy / grantedAt
F
AdminRoleAudit（审计）
actor / target / action / reason（必填）/ details(JSON)
🔌 API 端点设计 16 端点
所有端点前缀 `/api/admin/rbac/*`，需登录认证。
GET/api/admin/rbac/permissions/me
获取当前管理员的权限列表（含角色和部门）
GET/api/admin/rbac/roles
获取所有角色列表
GET/api/admin/rbac/roles/:role
获取指定角色的完整权限列表
POST/api/admin/rbac/roles
创建新角色（含权限配置），需 rbac.role.create
PATCH/api/admin/rbac/roles/:role
更新角色权限，需 rbac.role.edit
delete/api/admin/rbac/roles/:role
删除自定义角色（预定义角色不可删除），需 rbac.role.delete
GET/api/admin/rbac/users
管理员列表，支持 role / department / status 筛选
POST/api/admin/rbac/users/:userId/roles
分配角色给管理员，需 rbac.user.assign
delete/api/admin/rbac/users/:userId/roles/:role
撤销管理员角色，需 rbac.user.revoke，body 含 reason（必填）
GET/api/admin/rbac/permissions
权限定义列表，支持 category / active 筛选
POST/api/admin/rbac/permissions
创建新权限，需 rbac.permission.edit
PATCH/api/admin/rbac/permissions/:id
更新权限定义，需 rbac.permission.edit
GET/api/admin/rbac/audit
审计日志，支持 actor / target / action / 时间范围筛选
GET/api/admin/rbac/users/:userId/history
获取指定管理员的角色变更历史
PATCH/api/admin/rbac/users/:userId/status
启用/停用管理员账号，需 rbac.user.assign
📅 实施路线图 5周
按优先级分阶段交付，每阶段结束有可演示版本。
Week 1-2 · Phase 1

RBAC 基础框架

  • Prisma Schema 新增 4 个 RBAC 模型
  • Migration + 初始化权限数据（45项 + 7角色）
  • 创建 SUPER_ADMIN 账号（Frank）
  • 权限检查中间件 `requirePermission()`
  • 前端 `hasPermission()` / `usePermission()` Hook
  • 角色列表页面（只读）
Week 3 · Phase 2

管理员管理 + 审计

  • 管理员列表页面（表格 + 筛选）
  • 角色分配 / 撤销功能
  • AdminRoleAudit 审计日志记录
  • 审计日志查看页面
  • 批量分配角色（多选）
Week 4 · Phase 3

高危保护 + UI 优化

  • 二次确认弹窗组件（DangerButton）
  • 危险权限标记 + 高亮样式
  • 路由守卫（前端 + 后端双层）
  • 权限不足时的友好提示页面
  • 权限矩阵可视化页面（管理用）

数据隔离 + 临时权限

  • RBAC 自定义角色管理（创建 / 编辑）
  • E2E 测试覆盖权限边界
⚠️ 风险评估 5项
识别主要风险及缓解措施。

🔴 超管账号丢失

唯一超管账号丢失后，无法管理其他管理员。

缓解：至少保留 2 个超管账号；将第二个超管设为备用，存放在安全的密码管理器中。

🔴 权限越级访问

低权限账号通过 API 直接调用高权限接口。

缓解：所有 API 端点强制经过 requirePermission() 中间件；审计日志实时记录所有拒绝事件。

🟡 权限被误删

AdminPermission 记录被物理删除，影响线上角色权限。

缓解：使用 isActive 软删除，不物理删除；所有变更需 reason 记录。

🟡 权限与页面不匹配

前端隐藏了按钮但 API 未鉴权，或相反。

缓解：前后端双重鉴权兜底；使用 usePermission() 统一管理可见性。

🟢 过度限制影响效率

权限设置过细导致日常工作繁琐。

缓解：提供「复制角色」功能；ADMIN 角色作为默认权限集。
